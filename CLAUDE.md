# Pro ERP

Multi-tenant SaaS ERP — built with Next.js (App Router), Tailwind CSS, and Shadcn UI, deployable on Vercel. The backend is **Neon (serverless Postgres) via Drizzle ORM**: one shared database, every tenant-scoped table carries an `org_id` column. Attachments go to **Vercel Blob**. (Until 2026-09-16 this was a Google-Sheets-as-database / Google-Drive-as-storage app where each org pasted its own Sheet URLs — that architecture was fully migrated away and removed; see "The Postgres migration" below before assuming any doc, comment, or memory that predates it is still accurate.) Full setup instructions and architecture notes live in [README.md](README.md) — read that before making changes, but cross-check it against this file for anything storage-related, since the README may still describe the pre-migration Sheets setup until someone updates it.

## Status

### The Postgres migration (2026-09-16 to 2026-09-19) — read this first

The entire persistence layer was rewritten from Google Sheets to Neon Postgres, in six phases, each verified against live data before the next started, then closed out with a backend audit, a frontend audit, and an independent two-agent security review. This was a full replacement, not a wrapper — `googleSheets.ts`, `tenantSheets.ts`, `moduleSheets.ts`, `sheetUrl.ts`, `googleAuth.ts`, `googleDrive.ts`, and `platform/provisioning.ts` are all **deleted**, along with the `googleapis` dependency, the `/onboarding` wizard, and every "paste a Sheet URL" / "connect a Drive folder" screen.

- **Schema**: `src/db/schema/**`, one file per domain cluster (`platform`, `auth`, `settings`, `tasks`, `inward`, `inventory`, `ppc`, `fms`, `parties`). Every generated business ID (`VEN-xxxx`, `RUN-xxxx`, `ORG-xxxx`, ...) is the real Postgres primary key, verbatim — no surrogate integer/UUID keys were added, since these IDs were already load-bearing as string foreign keys everywhere (FMS's `Context_Ref` convention, `Form_Data`'s lookup-field `__id` stash, `BOM_ID`/`Template_ID`/`Instance_ID` grouping keys).
- **Generic data layer**: `src/db/repo.ts` — `listByOrg`/`findById`/`insertRecord`/`updateById`/`deleteById`, every one of them requiring `orgId` as a real argument, type-constrained to only work against tables with a plain `id` primary key. Tables with a **composite** primary key (`fms_templates` — `template_id, step_no`; `bom` — `bom_id, line_no`; `plan_materials` — `plan_id, sku`; `holiday_list` / `fms_weekoff_overrides`'s date-scoped queries) don't satisfy that type and get direct, bespoke Drizzle queries in their own domain file instead — **any query against one of these must still carry its own `eq(table.orgId, orgId))`, since `repo.ts` isn't there to enforce it for them.**
- **Migration tooling (switched 2026-09-21): real migration files now, not `drizzle-kit push`.** `drizzle/0000_mute_white_tiger.sql` is a baseline migration generated from the schema as it stood at cutover — it was never actually executed against the live DB (all 29 tables already existed); instead it was marked applied by hand-inserting its hash/timestamp into `drizzle.__drizzle_migrations` (the exact table/hash/timestamp scheme `drizzle-orm/neon-http/migrator`'s `migrate()` itself uses — read `node_modules/drizzle-orm/migrator.js` and `node_modules/drizzle-orm/neon-http/migrator.js` if this ever needs redoing), so `drizzle-kit migrate` correctly sees it as already-applied and no-ops on it. **From now on**: change `src/db/schema/**`, run `npx drizzle-kit generate` (writes a new numbered `.sql` file under `drizzle/` — review it before applying, this is the rollback/audit story `push` never had), then `npx drizzle-kit migrate` to actually apply it to the live DB. **Never run `npx drizzle-kit push` again** — besides being superseded, it's also the command that produced a real near-miss on 2026-09-21 (a mis-scoped `--tablesFilter` made it briefly plan to recreate the entire schema; caught before any damage, but see the `settings_org_id_key_unique` working note below for the underlying quirk that triggered it).
- **Caching removed**: `tenantCached`/`cached` (30s/60s TTLs that existed purely to survive Sheets' cost) are gone from every migrated path — a real indexed Postgres read replaced them, which also fixed several up-to-30-seconds-stale-data bugs the caching had introduced (a revoked report-share link, a just-deactivated user, a just-created org — all now take effect immediately, not "within 30 seconds depending which serverless instance you hit"). `src/lib/cache.ts` itself is untouched/unused now — nothing imports it.
- **Signup is simpler now**: no Sheet URL, no `verifySheetAccess` probe — just org name / admin name / email / password. `organizations.systemSheetId` was a real column through most of the migration (kept for continuity, always written as `""`) and was dropped outright once nothing read it.
- **Attachments are Blob-only now, unconditionally** — the old Drive-folder-connect option (`src/lib/googleDrive.ts`, `verifyDriveFolderWritable`, the "personal Drive has no quota" fallback dance) is gone. `src/lib/storage.ts`'s `uploadAttachment()` is a single unconditional call into Vercel Blob. `GOOGLE_SERVICE_ACCOUNT_EMAIL`/`GOOGLE_PRIVATE_KEY` are no longer read by any code path in the app — harmless to leave set in Vercel/`.env.local`, safe to remove whenever convenient.
- **Real bugs found and fixed during the migration's own audit passes** (worth remembering as patterns, see "Working notes" below for the durable lessons):
  1. `deleteOrganization()` only cascaded into 4 of 22 tenant-owned tables when first ported — deleting any org that had touched Tasks/Inventory/FMS/etc. threw a raw FK-violation instead of deleting. Fixed to cascade into all of them, atomically via `db.batch()`.
  2. The platform delete-organization confirmation dialog told the operator the org's data was untouched/safe — true under the old Sheets architecture, **false** now (deletion is a real, permanent wipe of every table). Copy corrected.
  3. `GET /api/fms/steps/[runId]` let any signed-in user in an org read *another* user's step context — including "Existing FMS" reference data such as a vendor's bank details — without being that step's assignee or holding `FMS_ADMIN`, even though the sibling complete-step endpoint already enforced exactly that check. Fixed.
  4. `plans.ts`'s local `hasFmsLine()` (a Sheets-era copy kept to avoid a real circular import with the FMS engine) would have silently always returned `false` post-migration — meaning `completePlan()` would double-write FG stock even when an FMS Line already wrote it via its own Action. Moved the real check into `fms/engine.ts` (which now owns `fms_runs`), `plans.ts` calls it via a dynamic `import()` to keep breaking the same cycle.
- **`DATABASE_URL` is now a required env var** (Neon's pooled connection string) — the app cannot boot any page without it, including login. Set on Vercel already; confirm it's set before ever pushing a change that touches this area to `main`, or production goes down immediately (every page needs the DB).

### New FMS capabilities added after the migration (2026-09-19)

- **Per-flow nav + Flow Board**: every Active FMS template gets its own nav item (gated to whoever has a step in it, or `FMS_ADMIN`) opening `/fms/[templateId]` — a dedicated board (one row per running instance, click for a stepper detail dialog) instead of everything mixed into the generic `/fms` tabs.
- **Linked "Lookup" form field**: an Admin can point a Form field at any connected module (e.g. Customers) and map other fields on the same step to autofill from the selected row — generic across modules, not hardcoded to any one of them. Runtime: `src/app/fms/complete-step-dialog.tsx`'s `LookupCombobox`; config: `FormFieldLookup` in `src/lib/fms/dataSource.ts`.
- **Admin-only full FMS reset**: a "Saare FMS Templates + Runs Reset Karein" button on the Templates board, gated on `role === "Admin"` (both client-side and by the API route via `requireRole`), requires typing "DELETE" to confirm — wipes every template and run for the org. For clearing test data built while designing flows, before real use begins.
- **TAT can now be in Minutes**, not just Hours/Days (`FmsTatUnit = "Minutes" | "Hours" | "Days"`) — the working-hours calendar math already worked in minutes internally, so this only needed the new unit threaded through `calendar.ts` and the builder UI.
- **Per-step WhatsApp notification list**: a step can name zero, one, or several users (independent of who the next step's own run goes to) who get a WhatsApp message the instant that step is marked complete. `fms_templates.notify_on_complete` (`text[]`); sent from `engine.ts`'s `notifyStepComplete()`, best-effort exactly like `emitFmsEvent`'s chaining — never blocks or fails step completion, every recipient sent in parallel, a recipient with no phone on file skipped silently, a real send failure logged.
- **A step's deadline can be sourced from an earlier step's own field, not just a fixed TAT** — tick "Deadline pichle step ke field se nikaale" in the template builder, pick the source step + field, and give an offset (+/-). This is what lets a single "Lead Days" number typed once drive multiple downstream deadlines (see Purchase FMS below).

### This session's build-out (2026-09-19 to 2026-09-21) — this is the "parent" section: keep it current

Everything below shipped in one long continuous session, each feature committed and pushed once the user confirmed it worked. **This section is the living master plan the user asked for — update it (don't replace it) every time a feature lands, rather than letting "Next up" silently go stale.**

- **Vendor ↔ Item linking** (`vendor_items` table, `src/lib/parties/vendorItems.ts`): a vendor-item pair carries its own lead time and unit price; `listVendorsForSku`/`listVendorsForSkus` sort cheapest-priced first (unpriced vendors sort last) and feed both the Reorder page's vendor suggestions and the Purchase FMS's PO Issue screen. The vendor-creation form is deliberately labelled "Purchase Vendor" (not just "Vendor") because OEM/Manufacturing vendor types may be added later and would need their own form.
- **Nav reorganized into dropdown groups** (`src/components/nav-links.tsx`'s `NavGroup`, assembled per-viewer in `src/components/app-shell.tsx`): **MDO** (Tasks/Flow/Leave/Reports/Performance), **PMS** (BOM/PPC/every FMS Line a plan actually starts), **Stock** (Inventory/Finished Goods), **FMS** (Inward/Purchase/every other flow), **Others** (Vendors-Customers/Users/Settings/Platform). A PPC-connected Line is told apart from an ordinary FMS flow by `triggerEvent === "PRODUCTION_STARTED"` OR actually being referenced by a plan (`listUsedFmsTemplateIds()`) — a Line's own default trigger is `MANUAL`, so the trigger alone can't be trusted.
- **UI motion pass** (applied via the `ui-ux-pro-max` skill + 21st MCP, "Standard" intensity): hover micro-interactions, scroll reveal, stagger lists across shared UI and key pages, without touching the existing color system, fonts, or accessibility behavior.
- **FMS TAT unit bug fixed**: `src/app/api/fms/templates/schema.ts` only allowed `Hours`/`Days` in its zod schema, silently rejecting the "Minutes" option the builder UI already offered. Added `"Minutes"` to the enum.
- **Purchase FMS — built as a hardcoded flow, not a generic FMS Template** (`src/db/schema/purchase.ts`, `src/lib/purchase/`, `src/app/purchase/`): Indent Approve (existing Indents flow) → **PO Issue** (vendor-first: pick a vendor, every Approved indent it supplies gets pre-suggested with old/new price, one PO can bundle several indents, PO attachment required) → **Follow Up** (a real actionable step, deadline = vendor's own lead time minus 1 day) → **Material Received** (invoice + per-item partial/full quantity, reusing the existing `receiveIndent` logic so stock updates identically either way). A new **Purchase Setup** admin screen (`/admin/settings`) sets each step's Doer + TAT (steps 3/4 need only a Doer — their deadline derives from the vendor's lead time). This satisfied the "Next up" Purchase FMS item below, but as bespoke screens rather than the originally-envisioned generic-FMS-Template configuration — reflects better because PO bundling/pricing needed UI the generic Form/Lookup model doesn't have a slot for.
- **Finished Goods split into its own Inventory view** (`/inventory/fg`, `InventoryBoard`'s new `scope: "goods" | "finished"` prop): one underlying stock model, but the main `/inventory` view now excludes `Category === "FG"` and the FG page shows only FG (and pre-selects "FG" on New Item). Both `completePlan()`'s stock-in and an FMS Production Line's final Action land here automatically — nothing else changed about how FG stock is written.
- **WhatsApp delivery bug fixed**: messages were silently failing (FMS step-complete notify, Task-completion confirmation) whenever a user's phone number lacked the "91" country-code prefix ChatXFlow's API requires. Fixed centrally in `sendWhatsAppMessage()` (`src/lib/chatxflow.ts`) via a `normalizePhone()` helper — a bare 10-digit Indian mobile gets "91" prepended, anything already prefixed or otherwise formatted is left alone.
- **Recurring Task generator's Sunday/holiday bug fixed** (`src/lib/recurringGenerator.ts`, fully rewritten): it previously only skipped explicit Holiday List dates, never the weekly-off day, so a Daily task assigned to run on a Sunday still fired. Now: **Daily** rules simply skip a non-working day outright; **Weekly/15D/Monthly/Quarterly/Yearly** rules carry a missed cycle forward to the next working day instead of losing it (via a per-frequency lookback window, `findMostRecentScheduledDay()`).
- **Holiday List admin CRUD added** (`src/lib/holidays.ts` rewritten from read-only; `src/app/admin/settings/holiday-list-form.tsx`, `src/app/api/admin/settings/holidays/**`): manual add, per-row edit and delete, and CSV/Excel bulk import (same download-template → fill → upload pattern as Items/Vendors/Customers). This list is *in addition to* the weekly-off day (set separately in FMS Shifts) — it exists for one-off extra non-working dates like festivals.
- **Leave System ("buddy system") built end to end** (`src/db/schema/leave.ts`, `src/lib/leave/{approvalSetup,leaves,reassignment}.ts`, `src/app/leave/**`, `src/app/admin/settings/leave-approval-setup-form.tsx`): a Doer files leave and picks their own Buddy; approval runs through a per-org configurable chain (`REPORTING_MANAGER` — resolved per-requester from `users.reporting_manager_id`, set at user-creation time — and/or one-or-more fixed `SPECIFIC_USER` steps like HR/MD); once every step approves (or the chain is empty), and the leave's date range includes today, **every currently-open Task and FMS step for the Doer reassigns to the Buddy** (`leave_reassignments` keeps a full audit trail so reversion is precise); ending the leave (or cancelling it) reverts only what is *still* Pending and *still* held by the Buddy — anything the Buddy already finished stays finished under the Buddy's name. Emergency Leave lets whoever holds the new `LEAVE_HR` module grant file on a Doer's behalf. **Deliberately deferred for v1, by the user's own explicit choice**: no leave balance/quota tracking (approval + reassignment only), and Payroll is a separate, later, not-yet-scoped conversation. Both `processLeaveTransitions()` (activate/revert) and the existing recurring-task generator now run together from one daily cron entrypoint (`runDailyJobs()` in `src/app/api/cron/generate-recurring-tasks/route.ts`).
- **Guidebook (`src/lib/guide.ts` / `guide.en.ts`) substantially expanded** to cover every feature above in plain, non-technical language, including new chapters for Parties (Vendor & Customer Master), Purchase, and Leave, plus new sections for the FG inventory split, the Holiday List screen, and the grouped nav bar — written for a layman reader, matching the existing chapter/section id parity `npm run i18n:check` enforces (79/79 as of this update).

### Modules (business features — mostly unaffected by the storage migration; described here in terms of what they do, not which database they used to use)

- **Module 1 — Auth**: custom email/password login, JWT session in an httpOnly cookie, role-based route guards (`src/proxy.ts`, `src/lib/auth/`). Password hashing (bcrypt), session payload shape, and every guard in `guard.ts` are unchanged by the migration — they only ever touched the JWT, never persistence directly.
- **Module 2 — Admin**: user management (`/admin/users` — create, edit role/status, reset password). `/admin/settings` now shows only genuine app configuration (Logo, WhatsApp/ChatXFlow, FMS Shifts, Week-off Overrides, Inward IQC TAT) — the old per-module "paste a Sheet URL" list is gone, since every module's table already exists in the shared schema.
- **Module 3 — Task Delegation**: one-time task assignment (`/tasks`) with Priority, Completion date & time, optional attachment, optional completion-proof upload (now via Blob unconditionally).
- **Module 4 — Dashboard & MIS**: per-user (`/dashboard`) and team-wide (`/performance`) MIS scoring (Done on Time / Delay Done / Not Done), computed dynamically from timestamps — nothing is a stored status flipped by a background job.
- **Module 5 — WhatsApp (ChatXFlow)**: token/phone/base-URL configured from Settings (per-org, in the `settings` table), completion-confirmation + pending-reminder automations for Tasks, daily Vercel Cron (`vercel.json`). FMS gained its own, separate WhatsApp use (per-step notify list, above) on the same `sendWhatsAppMessage()` primitive.
- **Module 6 — Inward FMS & IQC**: inward entry form (`/inward`), IQC quality-check modal, routing to Failure Log / IMS Inward on save. Working-hours-aware TAT/deadline (`IQC_TAT_Value`/`_Unit`/`_Deadline`, Admin-configurable in Settings), computed against a company-default shift since an inward entry has no single assignee to peg a shift to. **`Party_Name` is now wired to Vendor Master (2026-09-21)** — `VendorPicker` (`src/components/vendor-picker.tsx`) type-ahead suggests Active vendors from a new session-only `/api/parties/vendors/lookup` (id+name only, no bank/GSTIN — mirrors `/api/inventory/lookup`'s reasoning that recording an entry shouldn't require the full `PARTY_MASTER` grant); picking one sets the new `inward_iqc_fms.vendor_id` column alongside `Party_Name`. Deliberately still free text, not a forced Lookup: an inward entry can name a party that isn't in Vendor Master yet, so `vendor_id` is additive (empty when the typed name has no match) rather than blocking the entry.
- **Recurring Task Engine**: daily cron (`src/lib/recurringGenerator.ts`) generates dated occurrences per rule (D/W/15D/M/Q/Y), holiday-aware for every frequency, month-end-safe. A subtle date-handling bug was caught and fixed during the migration: `Due_Date`/`Assign_Date` must round-trip as IST wall-clock strings (`toIstWallStamp()`/`istDayKey()`), not plain UTC `.toISOString()`, because this generator does a raw `startsWith(todayIST())` string-prefix check — a naive ISO string would silently roll onto the wrong calendar day for anyone due between IST midnight and 5:30am.
- **Module 11 — Analytics dashboard** (`/dashboard` → Dashboard tab): per-module bar/donut/timeline charts, gated by the viewer's grants, with date-range filters in the URL so a view is shareable. Hand-rolled SVG in `src/components/charts.tsx`, no charting library. **No longer wrapped in `tenantCached`** — Postgres reads are fast enough that the 30s staleness this used to accept isn't needed; each read still degrades to `null` independently, so one broken module never blanks the rest.
- **MIS scoring is a penalty scale**: 0% is spotless, −100% the worst. On time costs nothing, late costs 0.5, missed costs 1, divided by tasks evaluated. `formatScore()`/`getScoreColorClass()` are the only display paths.
- **Module 10 — Organization logo**: optional at signup, changeable from Settings. Always Blob (never was Drive, unaffected by the migration) — renders on every page load and needs a CDN without an auth round-trip. Raster only.
- **Module 9 — Guidebook** (`/guide`, `src/lib/guide.ts`): the in-app manual, written as data, filtered per viewer by `guideFor()`. The onboarding/Sheet-connection sections were removed during the migration; add content by editing `GUIDE`, not by writing a page.
- **Module 8 — Recurring rule pause, quality records, platform console**: recurring rules can be paused/resumed from `/tasks`; Failure Log and IMS Inward are readable at `/inward`; `/platform` lists every organization and can suspend/delete one.
- **Module 8 — Per-user module access**: `Module_Access` (now a real `text[]` column on `users`, was a comma-separated string) + `src/lib/moduleAccess.ts`. Role is the privilege level; grants decide which modules a person works in. Baked into the JWT at login — `requireModule()` costs no DB read.
- **Module 7 — Multi-tenancy (SaaS)**: self-serve org signup (`/signup`, no onboarding wizard anymore). `organizations` + `users_index` are tables in the same shared Postgres database (used to be a separate "platform registry" spreadsheet Pro ERP itself owned) — login's first hop resolves an org from the email via `users_index`.
- **Module 12 — FMS (Flow Management System)**: a generic engine so a multi-step business process is built by an Admin as data (`/fms` → Templates), not code. `fms_templates` (one row per step, composite PK, mirrors the old flat-sheet shape on purpose), `fms_runs` (one row per step execution), `fms_weekoff_overrides`.
  - **Working-hours calendar** (`src/lib/fms/calendar.ts` + `workingCalendar.ts`, pure/zero-import): a TAT (now Minutes, Hours, *or* Days) counts only real working time — per-user `Shift`, lunch/tea excluded; weekly-off with date+department/user overrides; one open TAT per person, snapped forward through the calendar, never naively added on top of "now".
  - **Data Source is two independent, combinable pieces** (`src/lib/fms/dataSource.ts`): a Form, and/or columns live-pulled from any connected module or an earlier step of the same flow (`THIS_FLOW_SOURCE`) — plus, added after the migration, a **Lookup** field type (see above). `Data_Source_Type` is derived server-side, never trusted from the client.
  - **Action** (Stock Ledger Movement, `src/lib/fms/actions.ts` + `actionRunner.ts`) binds SKU/Qty/UOM from a dropdown of the step's own real field names. Unlike chaining, an Action's write must succeed before the step can complete — a bad SKU or insufficient stock throws and the step stays Pending.
  - **`emitFmsEvent()` is the one chaining primitive** — a completed FMS step, Inward (`INWARD_ENTRY_CREATED`), PPC (`PRODUCTION_STARTED`), and Indent approval (`INDENT_APPROVED`) all call it. Best-effort — a broken downstream flow must never undo something already saved. `notifyStepComplete()` (the new WhatsApp feature) follows the exact same best-effort convention, for the same reason.
  - **Production creates real stock.** `completePlan()` writes an FG stock-In for the quantity actually made, *unless* an FMS Line is already tracking the plan (`hasFmsLine()`, now living in `engine.ts`) — then the Line's own last-step Action writes it instead, at whatever quantity actually survived every stage, so production is never double-counted. **A plan's FG stock has exactly one writer at a time — never let both fire.**
  - **A production plan can name a specific Line** (`fmsTemplateId` on the plan) — `Start Production` then starts only that one template directly (`startFmsInstance`). **A plan with no Line chosen starts no Line at all (fixed 2026-09-21)** — this used to fall back to broadcasting `PRODUCTION_STARTED` to every Active template with that trigger, which meant two products each needing a different Line would both fire for any plan that hadn't picked one; that fallback is now removed, so `emitFmsEvent("PRODUCTION_STARTED", ...)` is no longer called from anywhere. The Line picker (`/api/ppc/production-lines`) deliberately offers every Active template regardless of its own `Trigger_Event`, since a Line's default trigger is `MANUAL` and nobody reliably retypes it.
  - **Templates are versioned like BOM**: editing (`updateFmsTemplate`) mints a new `Template_ID` and archives the old one rather than mutating rows in place — a running instance keeps resolving against the old, still-readable version.
  - A manual **"Start"** button on the Templates board is the only way to run a `MANUAL`-trigger template; every other trigger fires via `emitFmsEvent()`.
- **Module 13 — Vendor & Customer Master** (built 2026-09-16, `/parties`): manual "+ Add" dialogs plus CSV/Excel bulk-import (download template → fill → upload), mirroring the Items-master pattern. Both warn — without blocking — on a duplicate name (case/space-insensitive, checked against existing rows and within the same import file). Now also carries the Vendor↔Item link (lead time + unit price per pair) that Purchase and Reorder both read. This is the foundation the roadmap's Purchase/Sales/Accounts chains all still need; Inward's `Party_Name` is not yet wired to it (see Module 6 above).
- **Module 14 — Purchase** (built 2026-09-20/21, `/purchase`): the hardcoded Indent Approve → PO Issue → Follow Up → Material Received flow described above. `PURCHASE_FMS` module grant covers steps 2-4; step 1 (Indent Approve) uses the existing `INDENT_APPROVE` grant. Doer/TAT for each step comes from the "Purchase Setup" admin screen.
- **Module 15 — Leave (buddy system)** (built 2026-09-20/21, `/leave`): filing, multi-step approval, and Task/FMS buddy reassignment as described above. `LEAVE_HR` module grant is the only leave-specific grant — filing and approving your own chain's steps need no grant at all, since every signed-in user can potentially be a requester or a resolved approver.
- **Bug fixed 2026-09-21 — a BOM's own product never got an Items-master row.** `createBom()` only ever wrote the product's SKU onto the `bom` rows themselves — nothing created a matching `items` row, so the very first time `completePlan()` or an FMS Production Line's final Action tried to record that product's FG stock, it failed with "Items master me nahi hai / SKU nahi mila", even though the product had obviously already been planned and built via BOM. `createBom()` now auto-creates the Item (Category `FG`, UOM `PCS`) the first time a product's BOM is saved, if no Item already exists for that SKU — a second BOM version, or a product whose Item was already created by hand (e.g. as `Semi-FG`), is left untouched. Once the Item exists it shows up in Inventory/Finished Goods with Free/On Hand/ADC/ROP live like any other item; planning fields (Lead Time, Safety Factor, MOQ, Max Level) are still left blank for the Admin to fill in, same as any manually created item. `actionRunner.ts`'s own "Items master me nahi hai" error message was also reworded to match `completePlan()`'s (tell the user exactly what to do), while investigating the live report that surfaced this bug.
- **Inward's `Party_Name` wired to Vendor Master (2026-09-21)** — see Module 6 above for the shape (`VendorPicker`, `/api/parties/vendors/lookup`, `inward_iqc_fms.vendor_id`). Closes the item that was open in "Next up" since the Postgres migration.
- **Fixed 2026-09-21 — a production plan with no chosen Line no longer broadcast-starts every `PRODUCTION_STARTED` template.** Found while the user was verifying their first real Production Line ("Production Line 1") end to end: `src/app/api/ppc/plans/[planId]/route.ts`'s "start" action used to call `emitFmsEvent("PRODUCTION_STARTED", ...)` whenever a plan's `fmsTemplateId` was blank, which fires *every* Active template with that trigger — exactly the "two products, two Lines, one plan accidentally starts both" ambiguity that picking a Line was supposed to remove, just for the one case (no Line picked) nobody had closed off yet. Removed outright, by explicit user decision: a blank `fmsTemplateId` now starts no Line at all, full stop. `emitFmsEvent("PRODUCTION_STARTED", ...)` is consequently no longer called anywhere in the codebase (the function itself is untouched and still used for `INWARD_ENTRY_CREATED`/`INDENT_APPROVED`/step-to-step chaining).
- **Switched from `drizzle-kit push` to real migration files (2026-09-21)** — see "Migration tooling" above for the mechanics. `drizzle/0000_mute_white_tiger.sql` is the baseline (the schema as it stood at cutover, marked applied without being re-run, since every table already existed); every schema change from here on gets its own generated, committed, reviewable `.sql` file.
- **Module 16 — Lead FMS (built 2026-09-21, `/leads`)**: the first leg of the Sales chain — Lead capture (manual punch or bulk Excel/CSV import, template download, same warn-not-block-on-duplicate convention as Vendors/Items) → pipeline (`Qualify` → `Follow_Up`, loops on "Call Back Later" → `Meeting_Scheduled`, loops on "Reschedule" → `Negotiation` → `Quotation_Sent` → `Order_Confirmed`/`Lost` from anywhere). Every transition appends a `lead_activities` row — a lead is read as a timeline, not a single status cell, same convention as `leave_reassignments`. Built as its own hardcoded flow, not a generic FMS Template — same reasoning as Purchase (a pipeline board, bulk import, and a quotation grid all need bespoke UI the generic engine has no slot for). `LEAD_FMS` is the one module grant covering the whole flow.
  - **Quotation** (`src/lib/leads/quotations.ts`, `quotationMath.ts`, `quotationPdf.tsx`): mechanism adapted from a reference CRM the user handed over to learn from (their own separate project, not merged in) — a whitelist-grammar formula calculator for line quantities (e.g. typing `2.5*3+1.2` into a qty cell; hand-written recursive-descent parser, deliberately not `eval`/`new Function` since the string reaches the server), GST charged on goods-plus-freight, and a PDF built with `@react-pdf/renderer` (no headless-Chromium dependency — worth reusing for any future printed document, e.g. a real PO document generator) uploaded via the existing Blob attachment path (`uploadAttachment()`). Money stays plain `numeric` throughout — the reference's own integer-paise/integer-milli-qty scheme was deliberately NOT adopted, to stay consistent with how every other module in this codebase (Purchase, vendor_items) already represents money. `quotations` carries a real `(org_id, quotation_no)` unique constraint; `quotationNo` is allocated by reading the current highest number and retrying on a genuine collision — same shape as Purchase's PO numbering.
  - **Deliberately stops at "Order Confirmed."** Accepting a quotation only flips the lead's status and best-effort emits `emitFmsEvent("LEAD_ORDER_CONFIRMED", "LEADS:<leadId>")` — no `Order`/`Company`/`Contact` record is created. That is the next, separate module (see "Next up" below) to build against this exact event, the same way Purchase's PO Issue reacts to `INDENT_APPROVED`.
  - **"Quotation Setup"** (new admin screen, mirrors "Purchase Setup"): company letterhead, bank details, default subject/note/terms, GST% default, quotation-number prefix/start, validity days — all via the existing `settings` key-value store. Reuses the org's existing logo (`ORG_LOGO_URL`, Module 10) rather than a second upload.
  - **Walk-in quotations are done (2026-09-22)** — a "+ Nayi Quotation" action on `/leads`' own Quotations tab opens a dialog that either picks an **Existing Customer** (scoped to Customer Master rows *this salesperson themselves created* — `customers.createdBy`, via `/api/leads/customers-lookup`, needing only `LEAD_FMS` not `PARTY_MASTER`) or adds a **New Customer** on the spot (writes to the real Customer Master via the existing `createCustomer()`, then quotes it immediately). `createWalkInQuotation()` and the lead-driven `createQuotation()` now share one `insertQuotationRow()` so both agree on numbering/retry/Setup-defaults. Terms & Conditions has always been independently editable per quotation on the builder page (`quotation-builder.tsx`'s own Textarea, saved via the header PATCH) on top of Quotation Setup's org-wide default — confirmed working end to end via a live test after the user asked, not a new feature.
- **Module 17 — Order FMS (built 2026-09-22, `/orders`)**: leg 2 of the Sales chain. Two entry paths converge on one pipeline — **Lead-sourced** (an Accepted quotation with `order_id = ''` sits in Order FMS's own intake queue, mirroring Purchase's own Approved-indent candidate-finding; opening one maps every free-text `quotation_items` line to a real Item and confirms/creates the real Customer Master row behind it — a lead-driven quotation was never required to point at one — in a single atomic action, landing directly in `Payment_Review`) and **Direct** (a salesperson's own Order Form, real Items from the start via the existing `ItemPicker`, same Existing/New Customer picker as walk-in quotations, optional PO upload). **`Items_Pending` is a real schema enum value that is deliberately never actually persisted** — completing Step 1 is all-or-nothing (an order with unmapped lines has no real SKU to reserve against anyway), so no DB row ever sits in that status; a future session touching this should not assume it does.
  - **`Payment_Review`'s credit gate** (`workPaymentReview()`/`computeCreditPosition()` in `src/lib/orders/orders.ts`): a customer with no `creditLimit`/`creditDays` needs a real advance (`order_payments` sum `> 0`) before proceeding. A customer with credit gets both checks together — would this push their total outstanding (recomputed fresh every call, every non-Cancelled order's `orderValue` minus its own payments, summed — never a stored running total) over `creditLimit`, or does any of their orders sit unpaid past its own `createdAt + creditDays` — either trips `Credit_Hold`. Clearing one is a deliberate human action (`approveCreditHold()`), authorized to the org's configured **Credit-Hold Approver** (a specific person, set in the new "Order Setup" admin screen — deliberately NOT a module grant, per the user's explicit instruction that this varies by org and should be assignable the same place Doer/TAT already are) or an Admin override.
  - **`Stock_Check` adds a fourth stock-commitment source.** `positionFor()`/`buildItemStock()` (`src/lib/inventory/ledger.ts`) now take an `orderReserved` map alongside `committed` (raw material) and `inTransit`: `free = onHand − committed − orderReserved`. `orderReservedBySku()` (`src/lib/orders/orders.ts`) mirrors `plans.ts`'s own `committedBySku()` one level up the chain — sums `order_items.reservedQty` across orders in `Stock_Check`/`Dispatch_Pending`/`Ready_For_PDI`. Reserving processes one order's lines against currently-Free stock (`reservedQty = min(qty, free)`, `shortageQty = qty − reservedQty`) — **never writes `stock_ledger`**, a reservation is not a movement, same as a production plan's own reservation before `completePlan()` actually consumes it. A short line fires both a Task and a best-effort WhatsApp (`notifyShortage()`) to every `PPC_PLAN` holder (a new `listUsersWithGrant()` helper, since none existed — Admins implicitly included, same logic `effectiveModuleAccess()` already encodes).
  - **`Dispatch_Pending` → `Ready_For_PDI`** sets a commit date and best-effort emits `emitFmsEvent("ORDER_READY_FOR_PDI", "ORDERS:<orderId>")` — the seam a future PDI module (leg 3) picks up from, same pattern as `LEAD_ORDER_CONFIRMED`. Not built here.
  - `order_payments` is an append-only payment log, not full Accounts (no GL, no invoices) — just enough real structure for the credit gate to work off actual data instead of one "advance amount" guess; a future Accounts module should build on these same rows rather than duplicating them.
  - A new customer added inline during order entry starts with no `creditLimit`/`creditDays` (`createCustomer()` collects neither) — lands in the safe "needs an advance" branch until an Admin sets credit terms from Parties afterwards.

**Live** at https://pro-erp-chi.vercel.app (Vercel, `Mking697/Pro-ERP` → auto-deploys on push to `main`). `GET /api/health` reports the live commit, DB configured status, and which other env vars are set (no longer reports Google service-account presence — irrelevant now).

## Working notes for future sessions

- **Every Postgres query touching a tenant-scoped table must filter by `org_id`, sourced from `getTenantOrgId()`/`getTenant()` (`src/lib/tenant.ts`) — never from client input.** For a table with a plain `id` primary key, use `src/db/repo.ts`'s generic functions, which enforce this by construction. For a composite-PK table (`fms_templates`, `bom`, `plan_materials`, `holiday_list`, `fms_weekoff_overrides`), the file doing the bespoke query is fully responsible for adding `eq(table.orgId, orgId)` itself — this is exactly the class of file a security review should re-check first when anything in it changes.
- **`getTenant()` throws when it cannot resolve an org — it must never guess.** An explicit `runWithTenant()` context wins (used by cron), otherwise the session cookie decides. This rule predates and survived the migration unchanged.
- **Schema changes go through `src/db/schema/**` + `npx drizzle-kit generate` then `npx drizzle-kit migrate`, and are reviewed/applied directly by whoever is driving the session rather than by a subagent in passing.** (Before 2026-09-21 this was `drizzle-kit push`; see the "Migration tooling" note above for why and how the switch happened.) The convention this migration established: a subagent doing domain-file work that finds a real schema gap or bug (a missing column, a wrong type) stops and reports it rather than editing the schema itself; the session driver reviews and applies the fix, then migrates it live before the domain file gets adjusted to use it. This happened for real three times before the switch (a missing `plan_materials.uom` column, `fms_templates.next_step_map`'s string-vs-jsonb mismatch, and the new `notify_on_complete` column) — none of them caused a production incident specifically because a subagent flagged rather than silently patched around them.
- **`deleteOrganization()` (`src/lib/platform/registry.ts`) must cascade into every table that has an `org_id` FK to `organizations`.** Adding a new tenant-scoped table to the schema and forgetting to add its delete to this function's `db.batch()` means deleting any org that has touched that table throws a raw FK-violation instead of succeeding — this was the single most-recurring bug across the whole migration (hit and re-hit at three different points as new tables landed). When you add a table, grep this function and add it there in the same change.
- **`npx drizzle-kit push` is retired (2026-09-21) — don't use it, use `generate`+`migrate` instead (see "Migration tooling" above).** It's also the command that produced two real incidents on the same day, both worth remembering even though the tool itself is no longer in the workflow: (1) it cannot run non-interactively in this environment — it always stopped to ask "You're about to add `settings_org_id_key_unique` unique constraint... Do you want to truncate settings table?" even after that exact constraint already existed in the live DB (a real drizzle-kit introspection quirk on this composite unique constraint, confirmed via `pg_constraint`), and `--force` would have auto-approved whatever that prompt needed, up to and including truncating `settings` — never reach for `--force` to get past a confirmation whose actual effect you haven't read; (2) scoping it with `tablesFilter` in `drizzle.config.ts` to work around that prompt only filters the *current-DB* side of the introspection diff, not the desired-schema side, so it concluded every other table was "missing" and generated a bogus CREATE-TABLE-everything plan (caught before any damage only because it happened to hit `organizations` first and errored out). If `generate`+`migrate` ever needs a comparable non-interactive escape hatch, don't assume one exists without reading the actual CLI behavior first.
- **Platform-operator access is `PLATFORM_ADMIN_EMAILS`, never a role or a database column.** `requirePlatformAdmin()` 404s (not 403) to stay undiscoverable. An empty list grants nobody.
- Suspending an organization takes effect on its next request (`tenantFromOrgId` refuses a non-Active org) and deletes nothing — contrast with the real, destructive delete above.
- **`src/proxy.ts` must let self-authenticating API routes through** (`/api/cron/*`, `/api/whatsapp/send-reminders`) — Vercel Cron calls them with an `Authorization` header and no cookie; those routes check `CRON_SECRET` or an Admin session themselves.
- **`forEachActiveOrganization()` (`src/lib/platform/runner.ts`) is still sequential**, but the *original* forcing reason (every org sharing one Google service account's Sheets-API rate limit) is gone post-migration — kept sequential now for simplicity and easy per-org error isolation, not necessity. Revisit if a future cron job needs to run far more often or against many more orgs.
- **Adding a new key to `MODULE_ACCESS` does not reach anyone already signed in** — grants are baked into the JWT at login, so a session minted before the grant existed returns 403 for it, Admins included, until they log in again.
- **An FMS step's Ledger Movement Action is not best-effort — its chaining (`emitFmsEvent`) and its WhatsApp notify list (`notifyStepComplete`) both are.** A bad SKU or insufficient stock in an Action must throw and leave the step Pending, since the Action is the point of the step. A broken downstream flow, or a WhatsApp send failing (no phone on file, ChatXFlow not configured, network error), must never undo or block something already saved — don't make these match each other "for consistency," they're deliberately asymmetric.
- **FMS templates are never edited in place** — `updateFmsTemplate()` always mints a new `Template_ID` and archives the old one, so a running instance never sees its steps change underneath it mid-flow.
- **A production plan's FG stock has exactly one writer at a time** — either `completePlan()` (no FMS Line tracking the plan) or the Line's own final-step Action (`hasFmsLine()` returns true). Never let both fire for the same plan.
- **Every signed-in page renders inside `src/components/app-shell.tsx`**, which builds its nav from the viewer's own grants plus (new) their entitled FMS templates. Pages should not hand-roll their own nav.
- Mobile has not been assessed yet — see "Next up" above.
- **Before/after any change**: `npx tsc --noEmit`, `npm run lint`, `npm run build`, and `npm run i18n:check` should all stay clean. The last one matters more than it used to — several FMS features shipped this cycle with real UI strings that had no English translation; `i18n:check`'s "t() calls with no EN" count catches this immediately and should be 0 before calling a UI change done.
- Live-testing convention established this migration: a throwaway `scripts/*.ts` file (loads `.env.local` via `dotenv`, seeds a real org/user through `createOrganization`/`createUser`/`runWithTenant`, exercises the real code path against the actual Neon database, cleans up its own rows afterward via `deleteOrganization()`) is the standard way to verify a backend change actually works, not just that it type-checks. A few of these were left in `scripts/` as reusable examples (`verify-db-schema.ts`, `fms-live-test.ts`, `reports-shares-live-test.ts`) — most were deleted after their one-time use, which is also fine; they're disposable by design.
- **Any code sending a WhatsApp number to an external API must go through `normalizePhone()` in `src/lib/chatxflow.ts`, never read `users.phone` raw.** ChatXFlow silently drops a message with no country code — this failed with no error surfaced anywhere, for both Task-completion confirmations and FMS step-complete notify, until traced back to this one root cause.
- **A leave's Task/FMS reassignment only ever reverts what is *still* Pending and *still* held by the buddy** (`src/lib/leave/reassignment.ts`) — never blind-reverts everything the leave ever touched. This is deliberate: if the buddy already finished something during the leave, or a third party reassigned it again in the meantime, reverting it anyway would either resurrect finished work or steal it back from wherever it legitimately is now. Keep this asymmetry if this logic is ever touched.
- **`reassignment.ts` deliberately does not import from `leaves.ts`** — it reads `leaves` rows directly via `findById` to avoid a circular import (`leaves.ts` calls into `reassignment.ts` to activate/revert). If a future change wants to add a helper shared by both, put it in a third file rather than picking one side to import from the other.
- **The Holiday List and a shift's weekly-off are two separate, additive concepts — don't merge them.** Weekly-off (e.g. Sunday) is set per-org in FMS Shifts and repeats every week; the Holiday List is one-off extra dates (festivals, etc.) on top of it. Both are checked by the Recurring Task generator and by FMS's working-hours calendar, but they're stored and edited in different places on purpose — a UI that tried to unify them would stop an Admin from opening one specific Sunday without disabling the whole weekly-off rule (a real, if rare, need — see the "Week-off Override" mechanism in FMS Shifts).
- **Purchase FMS is a hardcoded 4-screen flow, not a generic FMS Template** — resist the urge to "clean this up" into the generic Template builder unless the builder actually grows a slot for vendor-first PO bundling and price snapshotting; forcing it into the generic model today would be a regression, not a simplification.
