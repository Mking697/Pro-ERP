# Pro ERP

Multi-tenant SaaS ERP with Google Sheets as the database and Google Drive as file storage — built with Next.js (App Router), Tailwind CSS, and Shadcn UI, deployable for free on Vercel. Any organization signs up, pastes its own Sheet URLs / Drive folder / ChatXFlow credentials, and gets an isolated system. Full setup instructions, sheet schemas, and architecture notes live in [README.md](README.md) — read that before making changes.

- **Module 2 — Admin**: user management (`/admin/users` — create, edit role/status, reset password), Google Sheets & Drive connections UI (`/admin/settings` — paste a URL, header rows auto-create on first write).
- **Module 3 — Task Delegation**: one-time task assignment (`/tasks`) with Priority, Completion date & time, optional Drive attachment, optional completion-proof upload.
- **Module 4 — Dashboard & MIS**: per-user (`/dashboard`) and team-wide (`/performance`) MIS scoring (Done on Time / Delay Done / Not Done), computed dynamically from timestamps — nothing is a stored status flipped by a background job.
- **Module 5 — WhatsApp (ChatXFlow)**: token/phone/base-URL configured from Settings, completion-confirmation + pending-reminder automations, daily Vercel Cron (`vercel.json`).
- **Module 6 — Inward FMS & IQC**: inward entry form (`/inward`), IQC quality-check modal, routing to Failure Log / IMS Inward sheets on save. Gained a working-hours-aware TAT/deadline (`IQC_TAT_Value`/`_Unit`/`_Deadline`, Admin-configurable in Settings) when the generic FMS engine (below) was built — purely additive, computed against a company-default shift since an inward entry has no single assignee to peg a shift to; `IQC_Status`, `Verified_By` and the Pass/Fail routing are all unchanged.
- **Recurring Task Engine**: `Recurring_Tasks` + `Holiday_List` sheets, daily cron (`src/lib/recurringGenerator.ts`) generates dated occurrences per rule (D/W/15D/M/Q/Y), holiday-aware for every frequency, month-end-safe.
- **Module 11 — Analytics dashboard** (`/dashboard` → Dashboard tab): per-module bar/donut/timeline charts, each section gated by the viewer's grants, with date-range filters (today/week/month/year/custom) in the URL so a view is shareable and the export matches what is on screen. Charts are hand-rolled SVG in `src/components/charts.tsx` — no charting library, server-rendered, tooltips via `<title>`. Colours come from a validated data-viz palette in `globals.css`: status steps (good/warning/critical) for state, series slots for identity, assigned in fixed order and never cycled. The warning step is sub-3:1 on light by design, so every chart also carries direct labels and a legend — colour is never the only cue. Aggregations live in `src/lib/analytics.ts` so charts, table and CSV export never compute a figure two different ways.
- **MIS scoring is a penalty scale**: 0% is spotless, −100% the worst. On time costs nothing, late costs 0.5, missed costs 1, divided by tasks evaluated. It cannot pass −100% by construction — no clamp needed. Changed from the earlier 0–100 credit score on the user's instruction; `formatScore()` and `getScoreColorClass()` are the only display paths.
- **Module 10 — Organization logo**: optional at signup, changeable from Settings, rendered in the header beside the org name (`ORG_LOGO_URL` setting, `OrgLogo` in `src/components/logo-picker.tsx`). The signup form sends the image as a data URL with the form rather than uploading first — at that point no org and no session exist, so a file endpoint there would accept uploads from anyone. Stored only after signup succeeds, and a logo failure never undoes the signup. Always blob, never the org's Drive: it renders on every page load and needs a CDN without an auth round-trip. Raster only — an SVG can carry script.
- **Module 9 — Guidebook** (`/guide`, `src/lib/guide.ts`): the in-app manual, written as data. Every section declares its audience (`everyone` / `admin` / `platform` / a module grant) and `guideFor()` filters to the viewer — a doer never scrolls past sheet-connection steps, an Admin gets the full setup walkthrough. Add content by editing `GUIDE`, not by writing a page.
- **Module 8 — Recurring rule pause, quality records, platform console**: recurring rules can be paused/resumed from `/tasks` → Recurring Rules (only `Active` rules generate); Failure Log and IMS Inward are readable at `/inward`; `/platform` lists every organization and can suspend one.
- **Module 8 — Per-user module access**: `Module_Access` column on the Users tab + `src/lib/moduleAccess.ts`. Role stays the privilege level (only Admin manages users/connections); grants decide which modules a person works in. An Admin ticks boxes per user; the grants are baked into the JWT at login so `requireModule()` costs no sheet read. Admins hold every grant implicitly.
- **Module 7 — Multi-tenancy (SaaS)**: self-serve org signup (`/signup`) + onboarding wizard (`/onboarding`). Each organization owns its own System spreadsheet; a platform registry sheet (`PLATFORM_SHEET_ID`) maps orgs and routes login by email. Every sheet read/write, cache entry, and cron run is scoped to one tenant.
- **Module 12 — FMS (Flow Management System)**: a generic engine so a multi-step business process — a deadline per step, an assignee, branching by outcome, one flow triggering another — is built by an Admin as data (`/fms` → Templates), not code by an engineer. `FMS_TEMPLATES` (flat rows per `Template_ID`, BOM's own shape), `FMS_RUNS` (one row per step execution), `FMS_WEEKOFF_OVERRIDES`.
  - **Working-hours calendar** (`src/lib/fms/workingCalendar.ts`, zero imports, mirrors `allocation.ts`): a "4 hour" TAT counts only real working hours — per-user `Shift`, lunch, optional tea break all excluded from the windows before the calendar ever sees them; weekly-off (default Sunday) with date+department/user overrides (`FMS_WEEKOFF_OVERRIDES`); one open TAT per person — a second assignment's clock starts only once the first's deadline actually arrives, snapped forward through the calendar, never added on top of "now" naively.
  - **Data Source is two independent, combinable pieces**, not an either/or (`src/lib/fms/dataSource.ts`): a Google-Forms-style **Form**, and/or columns **live-pulled** from any connected sheet or an earlier step of the same flow (`THIS_FLOW_SOURCE`), filtered to the running instance or left as an unfiltered lookup list. Both can be on at once — a real production step routinely types its own Pass/Fail while also needing to see the product's SKU pulled from elsewhere. `Data_Source_Type` is a display tag **derived server-side from the saved config**, never trusted from the client, so it can never drift out of sync with what's actually configured.
  - **Action** (today: Stock Ledger Movement, `src/lib/fms/actions.ts` + `actionRunner.ts`) binds SKU/Qty/UOM from a **dropdown of that step's own real field names**, never a typed string — a typo can't mis-wire a movement. Unlike the best-effort chaining hook, an Action's ledger write must **succeed before the step can complete** — it's the point of the step, not a side effect; a bad SKU or insufficient stock throws and the step stays Pending.
  - **`emitFmsEvent()` is the one chaining primitive** — a completed FMS step, Inward (after saving an entry: `INWARD_ENTRY_CREATED`), and PPC (Start Production: `PRODUCTION_STARTED`; Complete: `PRODUCTION_COMPLETED`) all call the same function. No loop guard — trusted to whoever wires triggers together, the same way a spreadsheet trusts whoever writes its formulas.
  - **Production now actually creates stock.** `completePlan()` used to only flip a plan's status; it now writes one `Production_Output` stock-In for the quantity actually made. When an FMS Line is already tracking a plan (any `FMS_RUNS` row against it — meaning `PRODUCTION_STARTED` was picked up by an Admin-built template), `completePlan()` **skips its own write**: the Line's last step records FG stock instead, at whatever quantity actually survived every stage, so production is never double-counted.
  - **Templates are versioned like BOM**: editing (`updateFmsTemplate`) writes a brand-new `Template_ID` and archives the old one rather than mutating rows in place — an instance already running keeps resolving its steps from the old, still-readable (Archived) `Template_ID`, so an edit made mid-flow never changes what a running flow does underneath it.
  - A manual **"Start"** button on the Templates board (`POST /api/fms/instances`) is the only way to run a `MANUAL`-trigger template — every other trigger fires `emitFmsEvent()` itself.

## Next up — configure the production Line, then Sales/Accounts, then Mobile

Original spec: **[docs/INVENTORY-PPC-PLAN.md](docs/INVENTORY-PPC-PLAN.md)** — fourteen decisions settled there (do not re-litigate them), phases 1-4 done, phase 5 below. Replaces a Google-Sheets + Apps Script system the user already runs. The short version:

- **Stock is derived from an append-only `Stock_Ledger`, never stored.** `free = on_hand − committed` is what PPC and reorder both read.
- **Reorder uses the fields their old system collected but ignored**: `ROP = ADC × Lead_Time × Safety_Factor`. Indent qty covers the shortage *and* tops up to Max Level, never below MOQ, and stays editable.
- **PPC allocates from a shared material pool, earliest production date first**, while still showing each product its own Done/Shortage status. Checking products independently is the mistake that makes two plans both read "Done" for the same stock.
- **Submitting a plan reserves material; Start Production (pressed by a Production Dept user) asks the actual quantity, writes the Out rows, and releases the leftover reserve.**
- A plan **snapshots its BOM**, so editing a BOM never rewrites history.
- Build order: (1) Items + ledger + In/Out + IQC auto-In → (2) ADC/ROP/reorder/indents → (3) BOM → (4) PPC → (5) production execution, Semi-FG, PDI, Packing, Dispatch.

**Phases 1, 2 and 3 are done and verified against live sheets (2026-08-20)**: `Items` + `Stock_Ledger` connected, item master, In/Out with the negative-stock block, live status/ADC/ROP, item detail with running balance, and IQC pass writing a stock In traceable to its inward entry. `ensureModuleHeaders()` (`src/lib/moduleSheets.ts`) now migrates any module sheet's header row, which is what let inward gain its `SKU` column without touching customers' sheets by hand. Phase 1 covers the item master, ledger, In/Out with the negative-stock block, live status/ADC/ROP, item detail, IQC pass writing a stock In, and Bulk Setup (`/inventory/setup`) for filling planning fields across many items — `updateModuleCells()` batches them into one Sheets write and touches only edited cells, so a bulk edit cannot clobber a name or category changed meanwhile. Phase 2 adds the reorder engine and indents: reorder compares **projected** stock (on-hand − committed + in-transit) against ROP so nothing already on its way is ordered twice; a `Pending` indent deliberately does not count as in-transit, or an unread approval would suppress a genuine reorder; receiving writes the stock In in the same action, because "mark received, then remember to add stock" is the step people forget.

Phase 3 adds the BOM: flat rows grouped by `BOM_ID`, the item picker fills SKU and UOM so a BOM can never carry a unit the item is not measured in, the same component twice is refused rather than summed, and re-saving a product's BOM writes a new version and archives the old one instead of overwriting it.

**Phase 4 — PPC is done and verified against live sheets (2026-08-20).** A plan reserves material the moment it is created; there is deliberately no unreserved draft state, because a draft reading "Ready" without holding stock is exactly how two plans come to depend on the same material. Products entered together are allocated from **one shared pool in production-date order** — `src/lib/inventory/allocation.ts` holds that calculation with **no imports at all**, so it can be run and reasoned about on its own (20 cases, including the plan doc's worked example). A `Shortage` plan reserves too: it is holding real material, and if it did not, the next plan would take what it already counted on and its shortage would grow silently. Start Production asks the **actual** quantity, checks every material against its allowance *before* writing any row (Sheets has no transaction to unwind a half-consumed plan), writes the `Out` rows, then sets `Allocated = Consumed` — which is what releases the leftover, since committed is measured as `Allocated − Consumed`. `Required_Qty` keeps what was planned. "Dobara check" re-allocates a short plan against current stock, without which a plan stays short for ever even after its indent arrives.

**Phase 5's foundation is done** (see Module 12, FMS, above) — `completePlan()` writes real FG/Semi-FG stock and fires `PRODUCTION_STARTED`/`PRODUCTION_COMPLETED`. What phase 5 originally meant (Semi-FG → IPQC → PDI → Packing → Dispatch) is now **pure in-app configuration on top of that engine**, not new library code — building the engine first was the point. **This is the very next thing to build**, in the running app itself:

- One FMS Template ("Line"), `Trigger: PRODUCTION_STARTED`, steps e.g. Winding → ... → IPQC → PDI → Packing → Dispatch, one Line per product family (a product needing 10 stages gets a 10-step Line, another needing 8 gets 8).
- Each step's Data Source: `Existing FMS` → `PRODUCTION_PLANS` (filtered to context) for the plan's own SKU/planned qty, `THIS_FLOW` → the previous step for its pass-qty, and/or a `Form` for what that stage itself captures (Pass Qty/Fail Qty, or for Dispatch: Transporter Name/Vehicle No/Vehicle Size as three plain fields — this is the entire "TMS" the user asked for, no separate module).
- The final step's Action: Stock Ledger Movement, `In`, bound to whatever quantity actually survived every stage — this is what writes real FG stock once a Line is used (see the `hasFmsLine` skip in `completePlan()` above).
- **Verify against live sheets**: Start Production on a real plan, confirm the Line's first step gets assigned, confirm pass-qty carries step-to-step, confirm the final step's stock write matches what actually survived (not the plan's optimistic actual quantity).

**After the Line works, three more chains are open — all pure FMS configuration once their one shared prerequisite exists, business-priority order is the user's call, not settled:**
- **Vendor & Customer masters** — foundational for the other two: `Party_Name` on Inward is free text today, and a real AP/AR ledger, an auto-filled PO, and the Sales chain's Order step all need a party to be a row, not a string.
- **Sales chain** — Lead Generation → qualify → Order Received → (checks FG stock) → PDI → Dispatch.
- **Accounts** — Payables against a PO, Receivables against a Sales Order, structured to grow into double-entry later rather than a flat payment log.
- **PO/document engine** — the user already runs a PO/quotation generator outside this app (crm.hicon.co.in) and will hand over its code to integrate, rather than rebuilding it from scratch.

**Mobile — the whole ERP needs to work well for a mobile user, not just resize down.** Not yet assessed, and needs its own discussion before building (this is a UX/architecture decision, not a small CSS tweak):
- Whether the existing Tailwind/Shadcn UI is already phone-usable end to end (nav, tables, dialogs — many screens are dense tables, which don't collapse to a phone width for free) or needs real rework.
- **One concrete gap already observed empirically, not guessed**: the top nav bar (`src/components/nav-links.tsx`) was seen overflowing and needing left/right scroll arrows even on an ordinary desktop browser window (not narrow) once enough modules were granted to one user — on an actual phone width this will be worse, and the nav is the one piece of chrome every single page depends on.
- Whether "mobile" means the responsive web app hardened (what exists today, works via any phone browser, zero app-store friction) or a wrapped/native app (installable, can do push notifications beyond WhatsApp, more work) — a real product decision, not a technical one alone.

- **Reports are one page each** (`/reports`, `/reports/<id>`), driven by `src/lib/reports.ts` — a single registry the index, each page, the share dialog and the public share page all read, because when each kept its own list they drifted. A report the reader has no grant for returns **404, not 403**, so the modules an organization runs cannot be discovered by trying URLs. Single-report mode also decides *what is read*: opening the inward report does not spend quota on inventory, BOM and PPC sheets. The dashboard's duplicated Tasks/Inward tabs are gone — those pages live in the nav, and each now has a report instead.
- **A share link carries one report, and personal reports cannot be shared at all** — a public link has no reader to be personal to, so it would be empty or somebody else's work.
- **Two bugs found by testing the share page, both worth remembering**: (1) `runWithTenant(tenant, () => <JSX/>)` does **not** cover an async child — React renders it after the parent returns, outside the AsyncLocalStorage scope, so `getTenant()` fell back to the cookie and the report came out empty. The tenant is now applied around the *awaited data fetch* inside `Analytics`, not around the element. (2) `/share` was in `PUBLIC_PATHS`, which also carries the "signed-in users get redirected home" rule — so any logged-in colleague opening a shared link landed on their own dashboard. `AUTH_PATHS` (login/signup only) now owns that redirect.
- **Adding a column to `REPORT_SHARES_HEADERS` in the middle broke every new link**: the sheet kept its old header, rows were written in the new order, and `Status` was read from the wrong column so links were born dead. `ensureSharesTab()` now **appends** missing columns and returns the sheet's own header, which writes follow — the same rule `ensureModuleHeaders()` uses.
- **Reports + public share links**: covering all ten modules (tasks, delegation, recurring, inward, IQC, IMS, inventory, indents, BOM, PPC), each section gated by the viewer's grants. A report can be shared as a **public read-only URL** (`/share/<token>`). The token lives in the **platform registry**, not the org's sheet — a visitor arrives with nothing but a token, so a per-org home would mean reading every org's sheet to find the owner, exactly the job `Users_Index` already does for emails. `/share` is in `PUBLIC_PATHS`; the page resolves its tenant **from the token alone and never from the session cookie**, or a signed-in visitor from another org would see their own data through someone else's link. The creator's grants are **copied onto the link** rather than read live, so being granted a new module later cannot silently widen a link shared months ago. Revoking deletes the row outright — there is no state left to flip back to Active.
- **Reports made the Sheets quota problem materially worse and are cached because of it.** One render can fire well over a dozen reads, and a share link puts that behind a URL anyone may refresh. `Analytics` wraps its whole read set in `tenantCached(orgId, ..., 30_000)`. This is the one place caching is right: a chart over a date range tolerates 30 seconds of staleness, where a stale *free stock* figure would let two people promise the same material — which is why the inventory screens still read live. Each read also degrades to `null` on its own, so one exhausted quota does not blank nine other modules' charts.
- **Users and organizations can be deleted.** Deleting a user removes the row and frees the email in the platform index, but leaves their tasks and records alone. Two refusals are built in: deleting yourself, and deleting the last active Admin. Deleting an organization ends its tenancy only — its own Google Sheets are never touched — and requires the org name to be typed back.

**Not done yet / next up:**
- **Attachment storage is hybrid** (`src/lib/storage.ts`). A service account has **zero Drive storage quota**, so uploading into a folder in anyone's *personal* My Drive fails with 403 "Service Accounts do not have storage quota" — even when the folder is shared and `canAddChildren` is true. Confirmed against a live folder 2026-08-19. Requiring a Shared Drive would leave every free-Gmail organization without attachments, so:
  - Org connected a **Shared Drive** folder → files go to its own Drive.
  - Otherwise (or if a Drive upload fails at runtime) → **Vercel Blob**, keyed `orgs/<orgId>/…` so tenants cannot collide. Needs `BLOB_READ_WRITE_TOKEN`, which Vercel injects once a Blob store is connected to the project.
  - Connecting a Drive folder runs a real upload-and-delete probe (`verifyDriveFolderWritable`), so an org learns at setup that a personal-Drive folder will not work — not later, when a user tries to attach a file.
  - **Verified on production 2026-08-19**: an org with a personal-Drive folder fell through to blob without losing the file, an org with no Drive folder went straight to blob, and both uploaded files fetched back as the exact bytes. Blob store `pro-erp-attachments` (Public, region bom1) is connected to the project; `GET /api/health` reports `blobStorage`.
- **Sheets API quota is the platform's scaling ceiling — and it was actually hit during development on 2026-08-20** (429, "Read requests per minute per user"). One developer testing alone reached it. It is a per-Cloud-project limit, not per organization, so it applies across every tenant at once. Batch reads where possible and keep an eye on it — every tenant shares one service account, so one Google Cloud project's per-minute limit is split across all organizations. Mitigated (batch reads, retry/backoff, per-org caches, sequential cron) but not removed; measure it before onboarding many paying orgs.
- No billing — every org is created on the `Free` plan and nothing enforces plan limits.
- Drive uploads capped at 4MB (Vercel Hobby body-size limit) — fine for images/PDF/Excel, not large video.

## Working notes for future sessions

- All Google API calls happen only inside `src/app/api/**` route handlers and server components — never in client components; the service account key must never reach the browser.
- Every business sheet (Tasks, Inward & IQC FMS, Failure Log, IMS Inward, Recurring Tasks, Holiday List) is its own separate Google Spreadsheet, connected per organization by pasting its URL in `/admin/settings` — not a hardcoded env var. The only env-configured spreadsheet is the platform registry, via `PLATFORM_SHEET_ID`; each organization's own System spreadsheet (`Users` + `Settings` tabs) is recorded in that registry at signup.
- **Platform-operator access is `PLATFORM_ADMIN_EMAILS`, never a role or a sheet column.** An organization Admin already reaches code that writes to the registry, so a stored flag could be granted to oneself. `/platform` returns 404 (not 403) to everyone else, so its existence is not advertised. An empty list grants nobody.
- Suspending an organization takes effect on its next request — `tenantFromOrgId` refuses a non-Active org — and deletes nothing.
- **Tenant isolation rules** — the three that matter, because breaking any one leaks customer data:
  1. `src/lib/googleSheets.ts` holds raw primitives that always require an explicit spreadsheet ID. `src/lib/tenantSheets.ts` wraps them and resolves the current org. Never add a "default spreadsheet" fallback to the raw layer.
  2. `getTenant()` (`src/lib/tenant.ts`) throws when it cannot resolve an org — an explicit `runWithTenant()` context wins, otherwise the session cookie decides. It must never guess.
  3. Anything read out of a tenant's sheets caches through `tenantCached(orgId, ...)`, never plain `cached()` — a warm serverless instance serves many orgs, and `Settings` holds each one's ChatXFlow API token.
- **`src/proxy.ts` must let self-authenticating API routes through.** Vercel Cron calls `/api/cron/*` and `/api/whatsapp/send-reminders` with an `Authorization` header and no cookie; when the proxy guarded them, every scheduled run was silently redirected to `/login` and never executed. Those routes check `CRON_SECRET` or an Admin session themselves — verified by real requests, not just by reading the code.
- Cron routes carrying `CRON_SECRET` run for every organization via `forEachActiveOrganization()` (`src/lib/platform/runner.ts`, sequential by design so one tenant's burst cannot 429 the rest); the same routes triggered by an admin session run only for that admin's org.
- **Adding a new key to `MODULE_ACCESS` does not reach anyone already signed in.** Grants are baked into the JWT at login so `requireModule()` costs no sheet read — the trade is that a session minted before the grant existed returns 403 for it, Admins included. Everyone must log in again after a new module ships. Hit for real when `PPC_PLAN` was added.
- Adding a column to `USERS_HEADERS` is safe: `ensureUsersHeaders()` appends any column the sheet's header row is missing, because `rowsToObjects` matches on the sheet's own header — a new column written without a matching header would be invisible on read.
- All sheet writes use `valueInputOption: "RAW"`. `USER_ENTERED` lets Sheets reinterpret input, which silently stripped the `+` from `+91…` WhatsApp numbers.
- Every signed-in page renders inside `src/components/app-shell.tsx`, which builds its nav from the viewer's own grants. Pages should not hand-roll their own nav.
- `src/lib/moduleSheets.ts` is the shared resolve/append/update/`recordToRow` layer every domain module (`tasks.ts`, `inward.ts`, `recurringTasks.ts`) is built on — extend it rather than re-implementing sheet I/O per module.
- **FMS templates are never edited in place** — `updateFmsTemplate()` always mints a new `Template_ID` and archives the old one (same reasoning as BOM's re-save). Never write a fix that mutates an existing template row directly, or an instance already running against it would see its steps change underneath it mid-flow.
- **An FMS step's Action is not best-effort, unlike its chaining.** `emitFmsEvent()` failures are always swallowed (a broken downstream flow must never undo something already saved); a Ledger Movement Action failure must always throw and leave the step Pending — it's the reason the step exists, not a side effect of completing it. Don't make these two match each other "for consistency."
- **A production plan's FG stock has exactly one writer at a time.** Either `completePlan()` writes it directly (no FMS Line ever started for that plan), or an FMS Line's own final-step Action writes it (when `hasFmsLine()` finds any `FMS_RUNS` row against the plan). Never let both fire for the same plan — that is a real double-count of physical stock, not a display bug.
- Mobile has not been assessed yet — see "Next up" above before assuming the existing responsive classes are sufficient on a phone.
- Before/after any change: `npx tsc --noEmit`, `npm run lint`, `npm run build` should all stay clean.
