PUBLIC API (import from @/lib/inventory/availability)
interface StockAvailabilityOptions {
  excludeOrderId?: string;
  excludePlanId?: string;
}
interface StockAvailability {
  onHand: Map<string, number>;
  orderReserved: Map<string, number>;
  planReserved: Map<string, number>;
  free: Map<string, number>;
}
interface StockRequest { sku: string; quantity: number; }
getStockAvailability(options?: StockAvailabilityOptions): Promise<StockAvailability>
assertStockAvailable(sku: string, quantity: number, options?: StockAvailabilityOptions): Promise<StockAvailability>
assertStockAvailableMany(requests: readonly StockRequest[], options?: StockAvailabilityOptions): Promise<StockAvailability>
StockAvailabilityError extends Error
InsufficientAvailableStockError extends StockAvailabilityError {
  readonly sku: string;
  readonly requested: number;
  readonly available: number;
}

MAP / EXCLUSION SEMANTICS
- Tenant comes only from getTenantOrgId(); no caller-supplied tenant override.
- onHand is unchanged by exclusions.
- orderReserved and planReserved are EFFECTIVE commitments after exclusions. They are not unadjusted display totals when options are supplied.
- free is round3(onHand - orderReserved - planReserved), on the union of all source keys. Reservation-only SKUs retain negative free; no clamping. Missing SKU reads as zero for assertions.
- Each supplied caller ID is queried verbatim with this tenant's orgId. Missing/foreign entities reject with StockAvailabilityError; empty/whitespace-only IDs reject before DB reads. IDs are not normalized.
- A verified caller exclusion removes ONLY its eligible still-unconsumed reservation rows, never the tenant's entire order/plan commitment map, never consumed stock, and never another caller's reservations.
- Existing non-reserving callers (Cancelled order; Completed/Cancelled plan; pre-stock order) are valid exclusions with zero effect. Both options may be supplied together.
- Errors from tenant resolution, ledger/commitment reads, or exclusion verification propagate unchanged. No catch-to-empty fallback exists.

ASSERTION / BATCH ADMISSION
- Nonempty SKU and nonempty request batch required. Requests must be finite and strictly positive, representable at round3 stock precision. Extra decimal quantities such as 1.0004, below-resolution 0.0001 and overflow quantities reject, not silently round down into unsafe admission. Small binary floating-point noise is tolerated.
- Normalize domain-derived quantities with existing round3 BEFORE assertion AND persist those same normalized quantities. Do not validate a rounded quantity then write a different raw quantity.
- assertStockAvailableMany aggregates duplicate SKU request lines into one demand per SKU before comparison, reads one availability view, and rejects requested > free. Unknown SKUs have zero free.
- Both assertion helpers return the availability view, make no writes, and do not decrement any in-memory or persistent pool.
- For any multi-line caller, use assertStockAvailableMany ONCE with the entire caller batch. Repeated single assertions without intervening writes are not batch admission and can over-admit.
- New insufficiency error is InsufficientAvailableStockError from availability.ts, NOT ledger.ts's InsufficientStockError. Integration must catch/translate the new error deliberately.
