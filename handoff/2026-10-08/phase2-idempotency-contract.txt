SECOND: durable idempotent mutation primitive — implementation contract

Source API (src/lib/mutations.ts):
  type MutationJsonValue = null | boolean | number | string | MutationJsonValue[] | { [key: string]: MutationJsonValue };
  interface TenantMutationOptions { operation: string; actorId: string; key?: string; payload: MutationJsonValue }
  runIdempotentTenantMutation<T extends MutationJsonValue>(orgId: string, options: TenantMutationOptions, work: () => Promise<T>): Promise<T>
  getMutationKey(request: Request): string | undefined
  MutationConflictError: Error, status=409, code="MUTATION_CONFLICT"
  MutationInputError: Error, status=400, code="MUTATION_INPUT_INVALID"

Integration:
- Invoke at the OUTERMOST money/receipt service boundary, replacing its top-level transaction wrapper. Nested entry is explicitly rejected BEFORE work. Domain work can use existing db and same-org runInTenantTransaction joins; do not invoke another idempotent mutation inside work. This restriction prevents ambient parallel replay races and swallowed-error partial commits without editing DB foundation.
- Key is tenant-wide and opaque, case-sensitive, 1–200 printable ASCII characters excluding whitespace. Never trimmed/case-folded. Missing undefined is allowed; empty, null, nonstring and malformed supplied keys reject. Header-only extraction has no Next dependency; Fetch Headers may already trim transport whitespace before application access.
- Pass the trusted authenticated actorId, a nonblank versioned operation identifier (e.g. accounts.bill-payment.create.v1), and JSON-safe parsed/validated domain payload. Scope authorization remains the caller's responsibility; receipt replay does not rerun work authorization.
- Hash is SHA-256 of stable canonical {actorId,operation,payload}; object keys sorted, array order preserved. Stored actor/operation are independently checked too. Bindings are snapshotted before awaiting admission.
- Existing READ COMMITTED tenant advisory lock is acquired before receipt read. A matching committed receipt returns stored JSON without invoking work. Mismatched actor/operation/payload throws typed conflict. Different tenants or different keys remain genuine independent mutations, including equal-valued payments.
- Receipt insert occurs after successful work on the same transaction. Work/result validation/receipt insert errors roll back both; failed attempts leave no receipt. No automatic retry. A committed:true post-commit failure retains the receipt; do not blindly retry it.
- Missing key retains transactional execution, with NO duplicate/replay guarantee. No amount-only deduplication.
- T is constrained to JSON DTOs, not Date-bearing database records. Explicitly project Date fields to ISO strings; unsupported Date, undefined, bigint, function, symbol, nonfinite number, class, accessor/nonenumerable/symbol property, sparse/augmented array, circular graph, NUL/unpaired Unicode surrogate reject clearly. Nesting limit 100 includes the binding envelope. Payload failure => MutationInputError; invalid work result => TypeError and rollback. First and replay results both use JSON representations; negative zero becomes zero. JSON null is stored via parameterized ::jsonb, NOT SQL NULL.
- Operation version must retain one consistent DTO contract across callers. No arbitrary domain-shape decoder is included, and lying casts/any cannot be runtime type-checked as a requested generic shape. Receipt rows are JSON-safety validated on replay.
- DB writes/builders must be inside work. afterTenantCommit effects are nondurable; no queue/outbox/general side-effect guarantee or receipt expiry policy was added. Existing lock/statement timeout failures can still reject contention rather than automatically retry.
