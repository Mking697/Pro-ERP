Phase Second transaction contract

Exports from src/db/client.ts:
- db: existing HTTP Drizzle API outside a scope; dynamically resolves methods (including captured relational query methods) to the active transaction inside a scope.
- runInTenantTransaction<T>(orgId, work): await all work. Validates nonempty tenant; same-tenant nesting joins; cross-tenant nesting rejects before another connection. No retry or global connection cache.
- isInTenantTransaction(): true only while admitted transaction work is active.
- afterTenantCommit(effect): queues by callback identity inside a scope, executes immediately outside. Each callback/batch savepoint region owns a separate effect Set; effects are merged into its immediate parent only after savepoint completion (including RELEASE) succeeds. Callback/batch failure or failed savepoint completion discards only that region's effects, retaining outer registrations of the same callback. A successful child followed by parent rollback is also discarded. Successful outer COMMIT triggers each distinct retained callback once, in retained Set insertion order (child effects enter the parent on successful completion), outside the transaction context; outer rollback discards them. Every retained callback is attempted even if another fails.

Each outer scope owns a one-connection Neon serverless Pool using the SAME DATABASE_URL as HTTP. READ COMMITTED; transaction-local lock_timeout=5s, statement_timeout=30s before parameterized pg_advisory_xact_lock(hashtextextended(orgId, 0)). Admission finishes before work. Pool acquisition budget 10s; release and pool.end always attempted. Original work/domain failure is preserved even when Drizzle ROLLBACK or cleanup fails.

Inside a transaction db.batch accepts lazy Drizzle builders created within the active scope, runs execute() sequentially and returns ordered results. Drizzle tx.transaction creates a SAVEPOINT on the SAME client; batch never commits independently. Failure rolls back the savepoint before a caught domain retry. Outside a scope, native Neon HTTP batch behavior is unchanged.

Awaited sibling db.batch and scoped db.transaction(callback) regions are FIFO-serialized on their owning connection/scope, including the SAVEPOINT command, callback, and RELEASE/ROLLBACK. The installed NeonTransaction.transaction uses sp${nestedIndex + 1}; siblings otherwise both create sp1. Unique names alone would not isolate overlapping savepoint lifetimes. Failed regions release the queue after rollback so later regions can retry. Scoped transaction callbacks receive a context-routed transaction proxy. Each callback/batch child scope uses the actual child Drizzle transaction and its own queue, so awaited nested callbacks, batches and same-tenant joins do not wait on their parent's held queue. Child savepoints therefore use the correct nestedIndex rather than reusing the parent sp1. Outside a scope, the original HTTP transaction implementation (unsupported) remains unchanged; nested transaction configuration follows installed Neon semantics.

Lifecycle: construct AND execute query builders within the owning transaction/callback scope. Do not let transaction builders or callback clients escape, do not pass builders created outside the owning scope or eager Promises to transactional batch, and do not start detached async work. Await all queries, batch/transaction regions and tenant scopes before their owning callback returns. Concurrent awaited sibling batches/transaction callbacks are supported; do not await a later queued sibling from an earlier held region, which creates an application-level circular dependency. Ordinary queries in another branch are not separately isolated: do not interleave them with a recoverable savepoint region. Wrap such work in an awaited scoped transaction callback or batch. Builder-lifetime and detached-work violations are documented contracts, not runtime-detected guards.

Post-COMMIT effect or resource-cleanup failures reject with an AggregateError carrying committed:true, result:<the committed work result>, and errors. Committed cleanup failure still attempts all deferred callbacks. Callers must NOT interpret this error as rollback or blindly retry committed writes. Effects themselves are not transactional/durable and have no automatic retry.
