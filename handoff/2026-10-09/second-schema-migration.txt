# Pending item 3 — dispatch shipment uniqueness reconciliation + coordinated migration

Status: implementation + local disposable-DB testing done. Stopped for parent review
before any further action. No production/deploy/commit/push/installs were performed.

## What was wrong

`src/db/schema/dispatch.ts` declared an unconditional
`unique("dispatches_org_id_shipment_id_unique").on(org_id, shipment_id)`, but no
checked-in migration had ever created it — the real `drizzle/meta/0028_snapshot.json`
only has `dispatches_org_id_gate_pass_no_unique`. Meanwhile
`tests/local-isolated/migrate.cjs` was separately, manually (outside migration
tracking) creating a table named the same and a **partial** unique index of the same
name (`WHERE shipment_id <> ''`) as a "LOCAL-ONLY" supplement after a duplicate
preflight check. Source and test harness disagreed on the actual invariant, and
neither was a real, checked-in migration.

## Decision: partial uniqueness, blanks preserved

Historical dispatch rows created before `shipment_id` was populated are blank (`""`,
the column's own default). The chosen, now-implemented policy is:

- `UNIQUE(org_id, shipment_id)` is enforced **only for nonempty `shipment_id`**
  (`WHERE shipment_id <> ''`). Legacy blank rows are never touched, deleted, or
  rewritten, and may coexist in any number per org.
- The tenant invariant that actually matters ("one dispatch per real shipment, per
  org") is scoped to real (nonempty) shipment IDs only.
- Before applying this migration to ANY database that already has real data,
  preflight for genuine duplicates:
  ```sql
  SELECT org_id, shipment_id, count(*) FROM dispatches WHERE shipment_id <> ''
  GROUP BY org_id, shipment_id HAVING count(*) > 1;
  ```
  If this returns rows, STOP — reconcile the duplicate stock/consumption/links by
  hand first. Never auto-delete history. Migration 0029 now also runs this exact
  check itself, server-side, as its first statement (see below).

## How migration 0029 was generated (no production/dotenv touched)

`npm run db:generate` was NOT run — it chains `db:check-sync`
(`scripts/check-migration-sync.ts`), which imports `dotenv`/`.env.local` and opens
`src/db/client`, i.e. a real/production-shaped `DATABASE_URL`. Explicitly avoided per
task constraints.

Instead: a scratch-only `drizzle-kit` config
(`pro-erp-generate-only.drizzle.config.ts`, kept outside the repo, deleted after use)
with only `{ schema: "./src/db/schema/index.ts", out: "./drizzle", dialect:
"postgresql" }` — **no `dbCredentials`, no dotenv import**. `drizzle-kit generate` only
diffs the TypeScript schema against the local `drizzle/meta/*_snapshot.json` chain; it
never opens a database connection for `generate`. Invoked directly via
`node node_modules/drizzle-kit/bin.cjs generate --config=<scratch config>` (no `npx`,
no network, no installs) with `cwd=G:/Pro-ERP` so the config's relative `schema`/`out`
resolved correctly.

The DO-block preflight guard was then added by hand to the generated SQL file (it is
not something `drizzle-kit generate` can produce — it's project-specific business
logic, not a schema diff).

## Local disposable-DB testing — what actually ran, and why the test shape changed

Backend verified healthy and reverified identity before touching anything:
`pro_erp_test` / `pro_erp_test` on the task-owned disposable container
(`pro-erp-regression-pg`/`pro-erp-regression-ws`, already running, not started/stopped
by this task).

**Important finding — isolated-schema "fresh install of all 30" is not achievable on
this shared disposable database, and that's a property of the generated SQL, not a
tooling gap:** every `CREATE TYPE` (enum) and every FK's `ALTER TABLE ... REFERENCES`
in every file under `drizzle/*.sql` hardcodes its target as literal `"public".name`,
regardless of `search_path` (checked across all 30 files — zero exceptions; every FK
in this project is `org_id -> public.organizations`). A `CREATE SCHEMA` +
`SET search_path` approach lets unqualified `CREATE TABLE`/`CREATE INDEX` statements
land in an isolated namespace, but replaying migrations 0000-0028 anywhere on this
same database immediately fails with `type "org_status" already exists` (etc.), since
those enums already exist for real in `public` from the actual applied baseline. The
only way to get a genuinely empty-to-30 install is a brand-new, empty **database**,
which `tests/local-isolated/safety.cjs`'s guard intentionally refuses to target (it
hard-pins `pathname === '/pro_erp_test'`) — correctly; weakening that guard was out of
scope and not done.

**What was actually run instead — `tests/local-isolated/migrate-0029-rollback-scoped.cjs`
(new file):** a single manually-driven transaction against the real, already-applied
baseline-29 `public` schema, using `SAVEPOINT`/`ROLLBACK TO SAVEPOINT` around each
sub-scenario so one scenario's expected failure doesn't abort the others, and a final
`ROLLBACK` (never `COMMIT`) so the database is provably bit-for-bit unchanged
afterward regardless of outcome. It:

1. Confirms exactly 29 migrations applied for real (sanity on the starting point).
2. Drops the earlier phase's untracked, non-migration `mutation_receipts` table and
   partial index (fully reversible — part of the same transaction that gets rolled
   back), so the rest of the test runs against a genuine pre-0029 state instead of
   that stray pollution. This directly addresses "existing local receipt
   table/partial index preadded outside migrations: cannot count running on those
   objects as fresh/upgrade proof."
3. Inserts a synthetic org + two legacy blank-`shipment_id` dispatch rows + two rows
   sharing a duplicate nonempty `shipment_id`.
4. **RED**: runs the actual checked-in 0029 SQL (read from disk, not hand-copied) —
   confirms it throws exactly the preflight's own exception, then rolls back to the
   savepoint and confirms `mutation_receipts`/the partial index still don't exist
   (abort happened before any DDL).
5. Deletes the synthetic duplicate's second row (test fixture, not real history) and
   re-runs the exact same 0029 SQL — **GREEN**: succeeds, creates `mutation_receipts`
   and the partial index (`WHERE (shipment_id <> ''::text)`, asserted verbatim),
   records the migration row itself (replicating what `migrate()` does), and confirms
   the two legacy blank rows are still there, untouched.
6. Confirms the invariant is enforced going forward: a new nonempty-shipment duplicate
   insert fails with the expected unique-violation message (in its own savepoint, then
   rolled back), while a third blank-shipment row for the same org still inserts fine.
7. Final `ROLLBACK` of the whole transaction.

Executed command and result (local disposable target, `PRO_ERP_LOCAL_TESTS=1` +
`PRO_ERP_LOCAL_CREDENTIALS=<scratch path>`, no dotenv):

```
node tests/local-isolated/migrate-0029-rollback-scoped.cjs
=> {"target":{"database":"pro_erp_test","username":"pro_erp_test"},
    "duplicatePreflightAbortsBeforeDDL":"PASS",
    "upgradeWithLegacyBlanksAndReconciledDuplicate":"PASS"}
```

Re-inspected the real `public` schema immediately after: still exactly 29 migrations
applied, the earlier phase's stray `mutation_receipts`/partial index still present
(restored by the rollback, exactly as found) — confirmed zero side effects.

`tests/local-isolated/migrate.cjs` was NOT re-run end-to-end against the live shared
`public` schema as part of this item, because it would now fail there for a reason
that has nothing to do with migration 0029's own correctness: the real `public`
schema already has the earlier phase's untracked `mutation_receipts` table and
partial index sitting in it (see above), so `CREATE TABLE mutation_receipts` inside
migration 0029 would hit "already exists". That cleanup is real and needs a decision,
not a test workaround — see Outstanding below.

## Outstanding / for parent review

1. **The live local disposable `public` schema is currently polluted** by the earlier
   phase's untracked `mutation_receipts` table + partial index (created by the old
   version of `migrate.cjs`, before this item's fix). It is NOT corrupted — the
   objects are structurally identical to what migration 0029 would create — but it
   means running the now-fixed `tests/local-isolated/migrate.cjs` for real (not
   rollback-scoped) will fail on "already exists" until someone decides: drop those
   two untracked objects from the live disposable DB for real (safe — they're
   provably identical to migration 0029's output, verified above), or recreate the
   disposable container from scratch. Did not do either unilaterally; this task's
   remit was reconciliation + preparation + rollback-scoped local testing, not
   mutating the live disposable target for real.
2. **Production preflight is still manual and unrun** — correctly so, per this task's
   explicit boundary (no production query/application). Before applying migration
   0029 to production: run the exact preflight query in this document's "Decision"
   section by hand first; if it returns any rows, stop and reconcile by hand (never
   auto-delete). Migration 0029 also re-runs the same check itself as its own first
   statement, so even an unreviewed `migrate` run fails closed rather than silently
   corrupting the invariant — but a human preflight pass is still the right first
   step operationally, so any needed reconciliation happens with full context rather
   than as a bare transaction abort.
3. **Rollback guidance if migration 0029 needs to be reverted** after a real apply:
   `DROP INDEX dispatches_org_id_shipment_id_unique; DROP TABLE mutation_receipts;`
   then delete its row from `drizzle.__drizzle_migrations` (match by `hash`). Nothing
   else this migration touches needs reverting — it adds exactly one index and one
   new table, no column/type changes to any existing table.
4. **Future sync-checker note**: `scripts/check-migration-sync.ts` only compares
   counts (`drizzle.__drizzle_migrations` row count vs local journal entry count) — it
   has no awareness of untracked, manually-added objects like the stray
   `mutation_receipts`/index above. That drift class (a real schema object that exists
   without a matching migration row) is exactly what bit this item; it's out of this
   item's scope to extend that script, but worth a follow-up idea: a periodic
   `drizzle-kit introspect`/`pull` diff against the live DB would have caught it
   immediately instead of only being discovered now.
