## 1. Reassignment + audit atomicity

**Before:** `activateLeave()`/`revertLeave()` ran a sequence of plain `updateById`/
`insertRecord` calls with no enclosing transaction. If the `leave_reassignments` audit
insert for entity N failed, entities 1..N-1's reassignment had already committed
individually (each `updateById`/`insertRecord` is its own implicit statement), with no
way to roll them back and no audit row for any of them — exactly the finding.

**Fix:** the entire body of `activateLeave()` and of `revertLeave()` now runs inside one
`runInTenantTransaction(orgId, async () => { ... })` (the established pattern from
`src/lib/fms/reset.ts`). Every `db.select`/`findById`/`updateById`/`insertRecord` call
already goes through the ambient tenant-scoped `db` proxy (`src/db/repo.ts`), so wrapping
the function body is sufficient — no call site needed to change. `recomputeRunTat()`
(dynamic-imported from `fms/engine.ts`) also issues its reads/writes through the same
ambient `db`, so it transparently joins the same transaction; `runInTenantTransaction`'s
own nested-call check (`active.orgId === orgId`) confirms this is safe, not accidental.

A failure anywhere now rolls back every reassignment + audit insert this call made, and
`activatedAt`/`revertedAt` is never stamped on a half-done pass.

## 2. Buddy resolution at task/FMS-run creation time

**Before:** `activateLeave()` only ever redirected work that existed at the moment the
leave activated. A recurring Task occurrence generated by cron *during* an already-active
leave used `rule.Doer_ID` verbatim — landing on the absent original doer until the next
`processLeaveTransitions()` run (which never actually catches it either, since
`activateLeave()` is a no-op once `activatedAt` is already set).

**Fix (in scope — Tasks only):**
- `resolveActiveAssignee(orgId, userId)`, new export in `reassignment.ts`: returns the
  buddy if `userId` currently has a leave with `activatedAt` set and `revertedAt` null,
  else `userId` unchanged.
- `recurringGenerator.ts`'s `generateDueRecurringOccurrences()` now calls
  `resolveActiveAssignee(orgId, rule.Doer_ID)` immediately before each occurrence's
  insert, for both the Daily and non-Daily code paths, and uses the result as
  `assignedTo`.
- `generate-recurring-tasks/route.ts`'s `runDailyJobs()` changed from
  `Promise.all([generateDueRecurringOccurrences(), processLeaveTransitions()])` to
  **sequential, leave first**. Rationale: `resolveActiveAssignee` reads live leave state,
  so a leave starting today must already be activated before today's recurring
  generation runs, or the outcome depends on which of the two concurrent promises'
  internal awaits happens to resolve first. This was a second, real ordering hazard
  inside the exact route file named in scope, not a hypothetical — fixed with a one-line
  reordering, no new dependency.

**Known residual gap — intentionally not fixed, out of this item's file scope:**
FMS run creation (`src/lib/fms/engine.ts`, e.g. `startFmsInstance`) has the identical gap
— a new run created during an active leave is still assigned to the original doer
verbatim — and the task description explicitly says "task/FMS run". Fixing it requires
editing `fms/engine.ts`, which is outside the three owned files/areas and the "one
additional file" allowance (that slot was used for the schema change, which is a harder
dependency of the already-in-scope recurring-generator fix). Flagging for a follow-up
item with `fms/engine.ts` in scope, rather than silently expanding scope.

**Also residual, lower severity:** `resolveActiveAssignee`'s read and `activateLeave`'s
transaction are not mutually synchronized — in the single leave-starts-today-with-no-open-work
case, if two *separate* cron invocations for the same org somehow overlapped (not the
normal single-invocation case this fix targets), a read could still observe pre-activation
state. This is a narrower residual than the Promise.all ordering bug (which is fixed) and
was not pursued further given minimal-scope intent.

## 3. Durable natural-cycle identity (cron-retry/concurrency safety)

**Before:** `generateDueRecurringOccurrences()`'s only "already generated" check was an
in-memory read of `existingTasks` taken once at the top of the function. Two concurrent
or retried invocations within the same cron run could both pass that check for the same
rule before either had actually inserted, producing two Task rows for the same cycle.

**Inspected first, per the instruction not to invent a new column:** `tasks` already has
`recurringId` and `dueDate` columns. Every occurrence this generator creates for a given
rule on a given day is deliberately all stamped with the *same* `dueDate`
(`${today}T23:59}` — true for both the Daily and the non-Daily/carry-forward paths, since
the carry-forward logic only ever shifts which day's cycle is *found*, never the due date
it's generated with). So `(org_id, recurring_id, due_date)` is already, exactly, that
rule's cycle-identity for the day it ran — no new column needed.

**Fix:**
- `src/db/schema/tasks.ts`: new partial unique index
  `tasks_org_id_recurring_id_due_date_unique` on `(org_id, recurring_id, due_date)`,
  scoped `WHERE recurring_id <> ''` so one-off (non-recurring) Tasks — which share no
  cycle concept — are never constrained by it.
- `recurringGenerator.ts`: `createOccurrenceIdempotently()` wraps the insert, catches a
  23505 unique-violation against that exact constraint name (same `cause`-chain-walking
  `isUniqueViolation` pattern already duplicated per-file elsewhere in this codebase —
  see `payables.ts`), and treats it as "already generated by someone else" rather than an
  error — incrementing the new `duplicatesSkipped` counter on `GenerateResult` instead of
  `created`, and letting the loop continue to the next rule. Any other error still
  propagates unchanged.
- Migration `drizzle/0031_tasks_recurring_cycle_unique.sql`: a `DO $$ ... RAISE EXCEPTION
  ... $$` preflight (same pattern as 0029/0030) that aborts the whole migration
  transaction with a clear message if any pre-existing duplicate
  `(org_id, recurring_id, due_date)` row already violates the new invariant, before the
  `CREATE UNIQUE INDEX` statement runs — generated via `drizzle-kit generate` against a
  scratch, no-dotenv, no-`dbCredentials` config (same safe pattern as the prior schema
  migration item), then the preflight block hand-added to the generated SQL, matching how
  0029/0030 were produced. `drizzle/meta/0031_snapshot.json` and `_journal.json`'s new
  entry are drizzle-kit's own unmodified output.
