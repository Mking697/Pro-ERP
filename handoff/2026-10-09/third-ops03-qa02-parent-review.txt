Source inspection (src/lib/auth/users.ts, read in full):
- updateUser() now wraps the ENTIRE read-decide-write sequence in
  runInTenantTransaction(orgId, async () => { const found = await getUserRow(...); ... }).
  getUserRow() — the authoritative read — executes AFTER the tenant advisory lock is
  acquired, not before. This is the actual fix for the claimed race (a stale copied Active
  row read before a concurrent deactivate+replacement-create committed): with the lock held
  for the full decide-then-write span, a second updateUser()/createUser() for the same org
  cannot observe pre-commit state from the first.
- assertActiveUserCapAvailable(orgId, plan) is called from INSIDE the same transaction in
  both createUser()'s insert path and updateUser()'s isReactivation branch — same shared
  helper, same lock scope, so create vs create / create vs reactivate / reactivate vs
  reactivate for one org genuinely serialize (keyed by orgId via runInTenantTransaction).
  Cap check only runs on genuine Inactive->Active transitions (isReactivation), matching
  the claim that profile-only edits, already-Active no-ops, and unlimited plans aren't
  gated. Confirmed by code reading, not just comment claims.
- Omitted-status contract: `...(patch.status !== undefined ? { status: newStatus } : {})`
  in the update .set() — status is never copied from a stale snapshot into a department-only
  patch. Confirmed present at line ~339.
- Last-admin guard: FOR UPDATE row lock inside the EXISTS subquery (anotherActiveAdminExists,
  lines 321-328) is unchanged/preserved and runs inside the same tenant-locked transaction —
  this is a real row lock, not cosmetic, and is independent of (additive to) the org-level
  advisory lock.
- Platform index update (updateIndexedUserStatus) remains POST-transaction (line 389-391) —
  exactly as the handoff discloses as a known-open item, not hidden.
