## Policy decision applied (explicit, documented, overridable — not a statutory ruling)

Problem reproduced exactly as given: `monthlySalary=20000`, `grossPay=0`, PF enabled →
old code: flat PF employee deduction 1800, `netPay = 0 - 1800 = -1800`.

Chosen default, documented in `statutory.ts`'s new `capDeductionsToGrossPay()` doc
comment:

- Employee-side deductions (PF + ESI + TDS) are scaled by the **same proportion**
  (`grossPay / totalRequestedDeductions`) rather than paying one deduction in full at
  another's expense, and rather than zeroing everything out across the board. A fixed
  PF → ESI → TDS order is used only as a rounding-safety valve (each capped by whatever
  of `grossPay` the previous ones left unclaimed), so the sum withheld never exceeds
  `grossPay` by even a rounding cent.
- Employer-side contributions (`pfEmployer`/`esiEmployer`) are left untouched — they are
  the org's own cost, not money withheld from the employee, so there's nothing to cap.
- Whatever couldn't be withheld is returned as `deductionShortfall` (non-persisted,
  attached only to `generatePayrollRun()`'s in-memory return as `GeneratedPayslip`) and
  logged server-side via `console.warn` (`[payroll] deduction shortfall for run ... user
  ...: requested X, grossPay Y, withheld Z, shortfall S`) — so it's visible immediately
  to the generator/reviewer and in server logs, never silently absorbed into a negative
  or a fictional number.
- Deliberately does NOT carry the shortfall forward to a future period automatically —
  flagged in the doc comment as a genuine payroll/compliance policy choice for a human
  to make.
- No schema/migration change: `deductionShortfall` is NOT a `payslips` table column.
  Persisting it durably (so e.g. `getPayrollRun()`/a past Finalized run's own view could
  show it again later) would need one — flagging this per the task's own instruction
  ("report first before adding") rather than silently adding a migration. If the parent
  wants it durable, that's a one-line schema addition (`payslips.deduction_shortfall`)
  plus a migration — did not do this.

## Serialized write boundary

`generatePayrollRun()` and `finalizePayrollRun()` each now wrap their entire
read-check-write sequence in one `runInTenantTransaction(orgId, ...)` call (same
tenant-advisory-lock pattern already used by `src/lib/maintenance/maintenance.ts`,
`src/lib/dispatch/dispatch.ts`, etc. — see `src/db/client.ts`). PDF generation in
`finalizePayrollRun()` stays OUTSIDE the transaction (unchanged, deliberately —
best-effort network/storage side effect, must not hold the lock or roll back the
already-committed status flip).

Net effect: two concurrent `finalize` calls for the same run can no longer both pass
the "not already Finalized" check before either writes — the loser's read now happens
only after the winner's write has committed, so it cleanly rejects
(`"Ye payroll run pehle se Finalized hai."`) instead of reprocessing
(double PDF generation, clobbered `finalizedBy`). Two concurrent `generate` calls for
the same month are serialized onto the same Draft run rather than racing its
find-or-create/upsert logic.
