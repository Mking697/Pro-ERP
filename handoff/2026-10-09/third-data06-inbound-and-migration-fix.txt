PART 1 — Inbound single/bulk ledger item SKU ownership admission
=====================================================================================

Problem found: src/lib/inventory/ledger.ts's recordMovement() (single) and
recordMovementsBulk() (bulk/import) never resolved/validated their SKU(s) against the
tenant's own Items master before writing a stock_ledger row — unlike the already-
approved vendor/BOM/Indent DATA-06 slices, a caller could record a movement (and every
caller does: inward.ts's IQC pass, inward/deviation.ts's Accept-Under-Deviation,
plans.ts's production consume/output, fms/actionRunner.ts's Stock Ledger Movement
Action, the bulk items-import's Opening Stock) for ANY string SKU — missing, typo'd, or
belonging to another tenant entirely — with no typed rejection and no admission check at
all. Every one of those six call sites already resolves/checks the item itself via
findItem() before calling recordMovement/recordMovementsBulk (so no production bug was
observed there), but the writer itself had no defense of its own — any NEW or future
caller (or a caller that forgets the check) would silently write ledger rows for an
unowned/foreign/missing SKU, exactly the class of bug DATA-06 already fixed for
vendorItems.upsertVendorItem() and bom.createBom().

Fix (src/lib/inventory/ledger.ts):
- New `LedgerAdmissionError` (typed, `status: 400 | 404`, defaults to 404) — same shape
  as IndentAdmissionError/VendorItemAdmissionError.
- New `admitOwnedItem(sku)`: resolves via the real tenant-scoped `findItem()` (same
  function every existing caller already uses); throws LedgerAdmissionError if the SKU
  doesn't resolve for the CURRENT tenant (missing or foreign-tenant-only both fail the
  same way, since findItem() is already org-scoped).
- New `admitOwnedSkus(skus)`: admits every DISTINCT SKU in a batch once (via a Set, not
  once per row) — a bulk writer must reject the WHOLE batch before any insert if even
  one SKU in it is unowned, never partially admit some rows and write the rest.
- `recordMovement()`: calls `admitOwnedItem(input.sku)` as the FIRST statement inside
  the existing `runInTenantTransaction(orgId, ...)` scope, before the existing
  `assertStockAvailable()` check and before the insert — admission failure never even
  reaches availability checking.
- `recordMovementsBulk()`: calls `admitOwnedSkus(inputs.map(i => i.sku))` as the FIRST
  statement inside the existing `runInTenantTransaction(orgId, ...)` scope, before the
  existing `assertStockAvailableMany()` aggregate check and before the insert.
- Both admission checks run under the SAME tenant lock/transaction the existing write
  already uses (runInTenantTransaction) — no new transaction boundary, no change to
  rollback/confirmed-commit semantics, which the real adapter
  (src/db/transaction-context.ts) already handles identically to the Indent/vendor/BOM
  slices (a thrown error before COMMIT rolls back; a post-COMMIT cleanup failure is
  reported with `committed: true, result` and must never be blindly retried).
- No change to any of the six call sites (inward.ts, inward/deviation.ts, plans.ts,
  fms/actionRunner.ts, movements/route.ts, items/import/route.ts) — each already passes
  a real tenant-resolved sku string; the new admission check is pure defense-in-depth at
  the writer itself, matching the DATA-06 pattern of "the domain/writer re-validates
  authoritatively, callers are not trusted alone."
- Not touched: validateMovementQuantity() (finite/positive/3-decimal check, unchanged),
  assertStockAvailable/assertStockAvailableMany (availability math, independently
  covered by tests/stock-workflow-unit.test.ts and stock-availability-policy.test.ts —
  mocked as a trusted boundary in the new focused test so this slice stays scoped to SKU
  ownership admission, not reimplement availability's own join logic).

PART 2 — Migration rollback harness: hardcoded total-migration-count fix
=====================================================================================

Problem found (as described in the task): tests/local-isolated/migrate-0030-rollback-
scoped.cjs and migrate-0031-rollback-scoped.cjs each asserted a hardcoded TOTAL checked-
in migration count (`allMigrations.length === 31` / `=== 32`) via drizzle-orm/migrator's
readMigrationFiles() and then indexed into that array by a hardcoded position
(`allMigrations[30]` / `allMigrations[31]`) to find "their own" migration. Both
assumptions go stale the moment ANY later migration (0032, 0033, ...) is checked in —
confirmed for real: drizzle/meta/_journal.json currently lists 32 entries (0000-0031),
so the 0030 script's own hardcoded "31" assertion was ALREADY wrong before this fix (it
would throw immediately on its very first assertion if someone tried to run it against
the real disposable target today). The SAME bug, same shape, was independently found in
migrate-0029-rollback-scoped.cjs (hardcoded 30/`allMigrations[29]`) — fixed too, since
leaving one of three near-identical sibling scripts with the exact same stale assumption
would just relocate the same class of bug, and the task's own instruction to "search
tests/ and scripts/ for a rollback harness referencing a hardcoded migration count" does
not scope that search to only 0030.

Fix (tests/local-isolated/runtime.cjs): new shared `resolveMigrationByTagPrefix
(migrationsFolder, tagPrefix)` helper — reads the REAL current drizzle/meta/_journal.json
directly (not a count passed in), finds the single journal entry whose `tag` starts with
the given numeric prefix (e.g. "0030"), asserts exactly one match exists, cross-checks
that readMigrationFiles()'s own returned array length matches the journal's own entry
count (so a future divergence between the two is still caught, not silently ignored),
and returns `{ migration: allMigrations[entry.idx], idx, totalMigrations, entry }` —
`allMigrations[entry.idx]` is guaranteed to be the SAME migration object the old
hardcoded `allMigrations[N]` indexing was already reaching for, just resolved by tag
instead of by a number that must be kept in sync by hand.

Each of the three scripts now calls `resolveMigrationByTagPrefix(migrationsFolder,
'0029'|'0030'|'0031')` instead of asserting a hardcoded `allMigrations.length` and
indexing by a hardcoded position. Every other assertion in all three scripts is
UNCHANGED and exact:
- migrate-0029: `before.rows[0].n === 29` (29 applied before 0029 runs, for real) — untouched.
- migrate-0030: `before.rows[0].n === 30` (30 applied before 0030 runs — i.e. the
  "30-applied disposable baseline guard" the task explicitly said to preserve exactly)
  — untouched; "migcount === 31" after the real upgrade (30+1) — untouched.
- migrate-0031: `before.rows[0].n === 30` (same 30-applied baseline — 0031 is scoped
  against the SAME pre-0030 starting point as 0030, by the original author's own design,
  since 0031 touches `tasks`, not `items`, and has no real schema dependency on 0030
  having run first in this isolated savepoint-scoped scope) — untouched; "migcount ===
  31" after the real upgrade (30+1) — untouched.
None of these three "applied-count" baseline numbers were the thing that was stale — only
the TOTAL CHECKED-IN FILE COUNT assumption was, and that is exactly what was fixed.
