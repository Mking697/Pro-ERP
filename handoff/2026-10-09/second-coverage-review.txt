HIGH-PRIORITY REMAINING SIBLING PATHS / ACTIONABLE FINDINGS

R1 [P1 DATA-01/07] Debit-note bill application bypasses the bill payment cap.
Owner: Finance.
src/lib/accounts/debitNotes.ts:475-482 checks vendor and Issued status, but :495-535
spends note balance and directly inserts billPayments without comparing amount with
billDetail.bill.amount - billDetail.totalPaid. In contrast payables.ts:474-478 caps
cash payments. A fully paid bill can receive another valid DN payment; two different
notes can exceed the same bill even though the common lock serializes both commands.
Required: same remaining-payable policy for EVERY billPayments writer, under admission;
regress cash-vs-DN and DN-vs-DN plus already-paid bill, rollback usage/payment/GL together.
CN application is likewise a direct orderPayments writer (creditNotes.ts:466-492), not
a call to recordPayment: parent must inventory this path independently, not infer its
activity/GL behavior from the nested three-argument Orders regression.

R2 [P1 DATA-03/04] Destructive FMS reset changes the FG-writer election.
Owner: Stock/PPC/FMS; parent must assign companion reset.ts explicitly.
src/lib/fms/reset.ts:20-26 deletes templates/runs via two independent ordinary queries,
without tenant lock. hasFmsLine (engine.ts:735-742) elects the output writer purely by
run existence; completePlan (plans.ts:608-627) writes FG when no run remains. Complete
a Line stock action while its plan is In_Production, reset FMS, then completePlan:
the historical Line stock remains but the evidence suppressing PPC output is gone.
Lock alone does not fix this sequential duplicate-output case. Guard reset against
real linked production/history or retain durable output ownership/event identity.
Regress sequential reset-after-Line-output and reset-vs-start/complete, not only normal
single-writer flow. This is a SECOND stock invariant companion, not a THIRD restart.

R3 [P1 DATA-04] Maintenance can overwrite an atomically completed FMS run.
Owner: Stock/PPC/FMS + parent-assigned narrow maintenance companion.
src/lib/maintenance/maintenance.ts:192-219 reads Pending then later unconditionally
sets Paused, without common admission; :316-324 and :476-479 can restore Pending from
stale Paused reads. If completeFmsStep commits between those reads/writes, maintenance
can clobber the terminal state; later resumption/completion can repeat the stock action.
Required: serialize these FMS status writers and conditional transitions with request/
activity work. Regression force breakdown/resolve/cancel versus stock-step completion.
Leave reassignment (leave/reassignment.ts:58,103) and recomputeRunTat(engine.ts:247-268)
are additional assignment/TAT writers to inventory; their broader OPS acceptance stays
THIRD, but assignee authorization must not rely on an uncontrolled stale read.

R4 [P1 DATA-03/04] Stock-in required auto-reservation work is still nondurable.
Owner: Stock/PPC/FMS + Orders, parent owns composition decision.
src/lib/inventory/ledger.ts:295,366 defers recheckReceivedSkus until commit; :310-316
catches all recheck failures and reports movement success. This is DB reservation/PDI
work, not an external notification. No durable retry intent exists. A new tenant
mutation may acquire admission after stock-in commits but before the recheck, spending
free stock ahead of older unmet Orders; failure can strand the shortfall indefinitely.
Required: if automatic/FIFO successor behavior is required, perform it in outer work
or persist recoverable work atomically. An afterTenantCommit Set is not an outbox.
Orders direct recheck now propagates errors and locks correctly; the enclosing ledger
caller still swallows them. Real stock tests mock recheck, so do not cover this seam.

R5 [P1 DATA-04] Standalone indent receipt and cancellation bypass PO lifecycle.
Owner: Purchase/receipts.

consistency and concurrent approval/PO claim/receive/cancel. Tenant lock is necessary
but not sufficient to make the siblings semantically consistent.
