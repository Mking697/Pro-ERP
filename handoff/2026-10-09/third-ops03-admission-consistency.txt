PART A — active-user cap: create vs reactivate consistency + concurrency
=====================================================================

PROBLEM (confirmed by reading the code first)
  createUser() (src/lib/auth/users.ts) already enforced the plan's maxActiveUsers cap
  (src/lib/platform/planLimits.ts) by counting Active rows before inserting. updateUser()
  had NO equivalent check on the Inactive -> Active (reactivate) transition — an org
  already at its cap could reactivate a disabled user and exceed it. Additionally,
  createUser()'s own pre-existing cap check was a plain "select count, then insert" with
  no locking at all — itself racy under two concurrent creates, despite the task's framing
  implying create already used a serialized check.

FIX
  Added `assertActiveUserCapAvailable(orgId, plan)` — the one shared helper both paths
  call. Both createUser()'s insert and updateUser()'s reactivate-path update now run
  inside `runInTenantTransaction(orgId, ...)` (src/db/client.ts / transaction-context.ts),
  the pg_advisory_xact_lock-backed primitive this codebase already uses elsewhere for
  "org-level serialized decision" problems (e.g. dispatch.ts's retry-scoped admission).
  The lock is keyed by orgId, so create vs create, create vs reactivate, and reactivate vs
  reactivate for the SAME org all serialize against each other; different orgs never
  contend. updateUser() only takes this path when the transition is actually
  Inactive -> Active (`isReactivation`); every other status/role/module-access change is
  unaffected, unwrapped, exactly as before. The pre-existing last-Active-Admin atomic
  guard (FOR UPDATE subquery folded into the UPDATE's WHERE) is untouched and still runs
  inside performUpdate() exactly as before.

PART B — background/cron tenant context trial-expiry policy
=====================================================================

PROBLEM (confirmed by reading tenant.ts and runner.ts first)
  Interactive requests resolve tenant context via getTenant() -> tenantFromOrgId(), which
  throws TenantResolutionError (digest TRIAL_EXPIRED) for an org whose 14-day Trial has
  lapsed — hard-blocking every read. forEachActiveOrganization() (src/lib/platform/
  runner.ts), used by every cron/background job, built its TenantContext directly from
  listOrganizations()'s raw row, filtering only `status === "Active"`. Trial expiry is
  independent of `status` (an expired-trial org is still "Active" status-wise), so cron
  kept generating new business records (e.g. recurring task occurrences) for an org whose
  own interactive users were already locked out.

POLICY DECISION APPLIED (documented, conservative, overridable default — per the finding's
explicit instruction, this is a stated choice, not a silent guess)
  Background/cron generation for a trial-expired org is now skipped entirely for that
  org's run. Implementation: runOne() now resolves tenant context via the SAME
  tenantFromOrgId() the interactive path already uses, instead of re-deriving it from the
  raw org row. This mirrors existing behavior rather than inventing a new independent rule
  (per the task's explicit instruction to read tenant.ts's real interactive handling and
  reuse it, not invent one). A trial-expired org's tenantFromOrgId() throws exactly like
  it does for an interactive request; the existing per-org try/catch in runOne() turns
  that into the same `{ ok: false, error }` shape every other org-specific cron failure
  already uses — it never aborts any other tenant's run.
  ALTERNATIVE FLAGGED (not implemented, remains valid): continue generating for a
  trial-expired org but mark the result/records read-only instead of skipping outright.
  If the business prefers that, src/lib/platform/runner.ts's runOne() is the one place to
  change — swap the tenantFromOrgId() call for a lighter check that still runs fn() but
  passes a read-only flag through ctx.
