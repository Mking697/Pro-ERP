WHAT WAS ACTUALLY BROKEN AND FIXED THIS SESSION
----------------------------------------------------------------------------
Promise.race timeout was NOT real query cancellation (the exact gap named in the
task). The prior route's checkDatabaseReadiness() went through the shared drizzle
`db` client from `@/db/client` (drizzle-orm/neon-http). Read
node_modules/drizzle-orm/neon-http/session.js's NeonHttpPreparedQuery.execute(): it
hardcodes its own `{ arrayMode, fullResults }` (or `{...,authToken}`) options object
on every call and has NO parameter for a signal/options passthrough from the caller.
db.execute() (drizzle-orm/pg-core/db.js) has no args for request-level options either.
So the previous Promise.race could only ever abandon *waiting* on the promise — the
HTTP request to Neon's data-proxy kept running server-side regardless of the route's
own timeout firing.

FIX: checkDatabaseReadiness() now imports `neon` from `@neondatabase/serverless`
directly (bypassing the shared drizzle `db` client for this one diagnostic probe
only — domain code elsewhere is untouched) and calls `sql.query(text, params,
{ fetchOptions: { signal } })`. Read node_modules/@neondatabase/serverless/index.js's
query-function implementation: `fetchOptions` IS spread directly onto the real
`fetch(url, { method: "POST", ..., ...fetchOptions })` call — `signal` there aborts
the actual outgoing HTTP request, not merely a local await. An `AbortController`
is created per probe; the existing setTimeout now calls `controller.abort()` in
addition to rejecting the race, so the real fetch is actually cancelled at the
network layer when the deadline fires.

HONEST LIMITATION (not oversold): this cancels the HTTP round-trip between this
process and Neon's HTTP data-proxy. It cannot force a query that has already been
handed off from the proxy to the underlying Postgres backend to stop executing
there — no client-side HTTP abort can do that; true statement-level cancellation
would need a separate `pg_cancel_backend`/`pg_terminate_backend` call keyed to the
exact backend PID, which neon-http's stateless HTTP protocol does not expose a PID
for per-request. This is documented in the route's own JSDoc and in README.md's
Deploy section, not glossed over. It is a genuine improvement (the wasted in-flight
HTTP request is actually torn down and its connection freed) but not "the database
stops running the query" — that claim is NOT made anywhere.
