## Generate/finalize contention + immutability evidence — reviewed, not re-litigated

Read `src/lib/payroll/payroll.ts` end to end and re-ran the prior slice's own
`tests/payroll-generate-finalize-unit.test.ts` (unmodified) to confirm its claims are
real, not just reported:

- Both `generatePayrollRun()` and `finalizePayrollRun()` wrap their entire
  read-check-write sequence in one `runInTenantTransaction(orgId, ...)` call
  (`src/db/client.ts` — real parameterized `pg_advisory_xact_lock(hashtextextended(orgId,
  0))` taken via `admit()` BEFORE any read, same contract every other domain
  (`src/lib/maintenance/maintenance.ts`, `src/lib/dispatch/dispatch.ts`) already uses).
  Confirmed by reading `src/db/transaction-context.ts`'s `runInTenantTransaction`: nested
  same-org calls join the existing scope (`work()` called directly, no second lock
  attempt — correct, since the outer transaction already holds the advisory lock for the
  whole org and a second same-connection `pg_advisory_xact_lock` call would just succeed
  redundantly, not deadlock); cross-org nesting is explicitly rejected.
- **Immutability**: `finalizePayrollRun()` throws `PayrollError("Ye payroll run pehle se
  Finalized hai.")` if `run.status === "Finalized"` — confirmed by test
  `"a second finalize on an already-finalized run rejects cleanly without reprocessing"`,
  which also asserts `finalizedBy` is NOT overwritten by the rejected second call.
  `generatePayrollRun()` similarly throws if the run is already Finalized, both at the
  initial read AND (defensively, documented as unreachable under the lock) immediately
  after an insert race.
- **Concurrent double-finalize**: test
  `"concurrent finalize calls for the same run cannot both succeed (serialized, not
  double-processed)"` fires two `finalizePayrollRun()` calls via `Promise.allSettled` at
  the exact same microtask — exactly one fulfills, exactly one rejects, and the row's
  final `finalizedBy` matches the winner (no silent overwrite). This is enforced by the
  DB-free mock's own serializing queue in the test file (mirrors
  `tests/fms-maintenance.unit.test.ts`'s pattern): a second `runInTenantTransaction` call
  for the same org genuinely waits for the first to finish before its own read runs — the
  same thing the real `pg_advisory_xact_lock` does against a real Postgres connection.
- **Concurrent double-generate**: test
  `"concurrent generate calls for the same month are serialized, not duplicated"` fires
  two `generatePayrollRun()` calls concurrently for the same month — asserts exactly ONE
  `payroll_runs` row for that month (not two) and exactly ONE payslip for the one seeded
  user (not two) — proving the find-or-create + upsert sequence cannot race itself into a
  duplicate.
- PDF generation in `finalizePayrollRun()` deliberately stays OUTSIDE the transaction
  (confirmed by reading the code — the `try { await generatePayslipPdfs(...) } catch`
  block runs after the `runInTenantTransaction(...)` call returns) — correct: it is a
  best-effort network/Blob-storage side effect that must not hold the advisory lock or
  roll back the already-committed Finalized status.

**Not added by this slice**: no real-PostgreSQL contention test (the prior slice's
DB-free mock proves the serialization logic; it does not prove the real
`pg_advisory_xact_lock` call against live Postgres behaves identically under genuine
network concurrency). This mirrors every other THIRD-phase domain's own current state
(DATA-06, OPS-01, OPS-03 all still lack real-PG contention runs per CLAUDE.md) — flagged,
not silently treated as done, consistent with the checkpoint's own item 8

actually populated in the PDF rather than just wired-but-dormant):
