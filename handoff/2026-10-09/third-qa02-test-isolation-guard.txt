## 1. Fail-fast disposable-target guard (tests/setup.ts)

**Problem confirmed by tracing actual files:** `tests/setup.ts` only ever called
`config({ path: ".env.local" })` — zero validation of the resulting `DATABASE_URL`. Checked
the actual `.env.local` in this workspace: `DATABASE_URL` points at a Neon database named
plainly `neondb`, with nothing in the name/host marking it disposable. Every real-DB test
in the default suite (`vitest.config.ts` → `setupFiles: ["./tests/setup.ts"]`, matching all
of `tests/**/*.test.ts`) was running against that target with no verification it's a
safe/disposable database — exactly the gap QA-02 flagged, distinct from
`tests/local-isolated/safety.cjs`'s existing hard pin (untouched, still correct).

**Fix:** extracted a pure, directly-testable guard:
`assertDisposableDatabaseTarget(databaseUrl, expectedPattern)` in
`tests/helpers/databaseTargetGuard.ts`, wired into `tests/setup.ts` right after
`dotenv.config()`, checked against `process.env.TEST_DATABASE_URL_PATTERN`.
- No pattern configured → throws (refuse-if-unset, never "trust it").
- `DATABASE_URL` unset → throws.
- Pattern is an invalid regex → throws.
- `DATABASE_URL` doesn't match the configured pattern → throws.
- Matches → passes silently.

Added `TEST_DATABASE_URL_PATTERN: ${{ secrets.TEST_DATABASE_URL_PATTERN }}` to the
job-level `env:` in `.github/workflows/ci.yml` (alongside the existing `DATABASE_URL`)
so CI can declare its own safe expectation — this is a genuine new requirement, not a
config fix left broken: whoever manages CI secrets must set `TEST_DATABASE_URL_PATTERN`
or the `Test` step will now correctly refuse to run. Documented in a comment in the
workflow file. This is intended: the guard is supposed to block running against an
unverified target, and the currently-configured local `DATABASE_URL` (`neondb`, not
obviously disposable) is exactly the kind of target it should block until someone
explicitly declares a safe pattern.

## 2. Loud setup/cleanup failures (tests/helpers/testOrg.ts)

**Problem confirmed by tracing:** `makeTestOrg` itself already throws on failure (no
swallow there). The actual leak path was structural: `runner-concurrency.test.ts` does
`const orgs = await Promise.all([makeTestOrg(...), ...])` — if any one creation in the
batch rejects, `Promise.all` discards references to the ones that *did* succeed before the
`try { ... } finally { cleanup }` block is ever entered, so those already-created orgs
become invisible orphans. Separately, its `finally` block's cleanup used
`deleteOrganization(o.id).catch(() => {})` — a cleanup failure is silently swallowed.

**Fix (within owned `tests/helpers/testOrg.ts`):** added two exported helpers using
`Promise.allSettled` so partial failures are tracked rather than discarded:
- `makeTestOrgs(labels)` — creates a batch, and if any creation fails, deletes every org
  that *did* succeed before re-throwing an `AggregateError` with all failure reasons. No
  silent partial-success leak.
- `cleanupTestOrgs(orgs)` — deletes a batch and throws an `AggregateError` (naming the
  orphaned org IDs) if any deletion fails, instead of swallowing it.
- `filterOwnResults(results, ownOrgs)` — see scoping section below.

Not wired into `tests/runner-concurrency.test.ts` itself (out of scope for this item —
not an owned file); the primitives are implemented, tested, and ready for that file's
owner to adopt.

## 3. Runner-concurrency scoping

Traced `tests/runner-concurrency.test.ts`'s actual current query (not the stale cited line
numbers — file is now 104 lines, finding cited 29-65). It already does inline scoping:
`results.filter((r) => expectedIds.has(r.orgId))` before every assertion in both `it`
blocks — unrelated organizations already on the shared DB (visited because
`forEachActiveOrganization` enumerates *all* active orgs by design) are excluded from
assertions. That inline logic is exactly what `filterOwnResults` in `testOrg.ts` now
formalizes and tests with a sentinel-foreign-ID case (see above). Since
`tests/runner-concurrency.test.ts` is not an owned file for this item, it was not edited
to call the new helper — the tested, reusable scoping primitive is available for whoever
owns that file to adopt in place of the inline filter.
