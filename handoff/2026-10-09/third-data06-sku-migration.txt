## Migration SQL (drizzle/0030_fine_dexter_bennett.sql, final)
```sql
-- DATA-06 preflight (DO-block, mirrors migration 0029's own pattern): aborts the whole
-- migration transaction before any DDL if duplicates/NULLs would violate the new key.
-- Mathematically defensive-only: the OLD constraint (sku alone, platform-wide unique)
-- is strictly stricter than the NEW one (org_id, sku), so no row satisfying the old
-- constraint can violate the new one. Included anyway per CLAUDE.md's "even an
-- unreviewed migrate run fails closed rather than silently corrupting the invariant."
DO $$
DECLARE
  dup record;
  nullorg record;
BEGIN
  SELECT org_id, sku, count(*) AS n INTO dup
  FROM items GROUP BY org_id, sku HAVING count(*) > 1 LIMIT 1;
  IF dup.n IS NOT NULL THEN
    RAISE EXCEPTION 'Migration 0030 preflight failed: duplicate (org_id, sku) rows exist
      in items (org_id=%, sku=%, count=%). Reconcile duplicate item masters/stock
      ledger/BOM/indent references by hand before retrying; never auto-delete history.',
      dup.org_id, dup.sku, dup.n;
  END IF;
  SELECT sku INTO nullorg FROM items WHERE org_id IS NULL LIMIT 1;
  IF nullorg.sku IS NOT NULL THEN
    RAISE EXCEPTION 'Migration 0030 preflight failed: items row with sku=% has a NULL
      org_id; the new composite (org_id, sku) primary key cannot include a NULL
      column. Reconcile before retrying.', nullorg.sku;
  END IF;
END
$$;
--> statement-breakpoint
ALTER TABLE "items" DROP CONSTRAINT "items_pkey";--> statement-breakpoint
ALTER TABLE "items" ADD CONSTRAINT "items_org_id_sku_pk" PRIMARY KEY("org_id","sku");
```
This is the entire migration — exactly one DROP CONSTRAINT and one ADD CONSTRAINT, no
column/type changes, no data rewrite, no other table touched.

## Application-code fan-out found — reported, NOT fixed (out of this item's scope)
**`src/lib/parties/vendorItems.ts:61`**:
```ts
.leftJoin(items, eq(vendorItems.sku, items.sku))
```
This join matches ANY `items` row with the same `sku`, regardless of org — it does not
also constrain `items.orgId = vendorItems.orgId` (the surrounding `.where()` only scopes
`vendorItems.orgId`/`vendorItems.vendorId`, not the joined `items` side). Under the OLD
platform-wide-unique-sku schema this was harmless (at most one `items` row could ever
match a given sku, period). **Once this migration is applied and two different orgs
hold the same SKU, this join can return another organization's item name/UOM
(`listVendorsForSku`'s underlying query) instead of — or in addition to — the calling
org's own item.** This is a genuine cross-tenant data leak introduced by the schema
change, needs `and(eq(vendorItems.sku, items.sku), eq(vendorItems.orgId, items.orgId))`,
and is domain logic, not schema — out of this item's remit per the task's own
instruction to stop and report rather than silently expand scope. Recommend a dedicated
follow-up item (or folding into whichever item eventually applies migration 0030 for
real) before this migration is applied to any database with real multi-tenant SKU
overlap.

No other `items`/`sku` join site was found anywhere outside schema files that omits an
org_id-scoped predicate — `src/lib/inventory/items.ts`'s own three sku queries (find/
update) already filter on `and(eq(items.orgId, orgId), eq(items.sku, sku))`, and
`repo.ts`'s generic `findById` cannot even be called against `items` (it requires a
single `id` column; `items`'s own doc comment already excludes it, unaffected by this
change either way).
