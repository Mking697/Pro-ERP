## 1. FMS run creation now uses the ACTIVE holder, with audit, atomically

**Before this pass** (confirmed by reading `fms/engine.ts` before editing):
`appendStepRun()` — the single internal helper both `startFmsInstance()` (a flow's first
step) and `completeFmsStep()`'s `createRun()` (every successor step) call — used
`input.assignedTo` (the template step's configured `Assigned_To`, or the prior step's
successor-step `Assigned_To`) verbatim for both the real DB row's `assignedTo` column AND
the TAT computation (`queueOpenTatStart`/`computeTatDeadline`). A step whose configured
assignee was currently mid-leave got a new run born on the absent doer, with a TAT window
computed against the absent doer's own working calendar — exactly the gap v1's "Known
residual gap" section flagged and explicitly left unfixed.

**Fix:** `appendStepRun()` now calls `resolveActiveAssigneeWithAudit(input.orgId,
input.assignedTo)` (dynamic import, breaking the same leave<->fms circular-import shape
`reassignment.ts`'s own `recomputeRunTat()` call already avoids) before doing anything
else. The resolved `assignedTo` — the buddy, if the step's natural assignee is currently
mid-leave, else unchanged — is used for:
- `queueOpenTatStart`/`computeTatDeadline` (the buddy's own working-hours calendar, open-
  TAT queue, shift/lunch/weekly-off — not the absent doer's).
- The inserted `fms_runs.assigned_to` column itself.
- A `leave_reassignments` audit row (`entityType: "FMS_RUN"`, `originalAssignee` = the
  step's own configured assignee, `buddyId` = the resolved active holder), inserted
  immediately after the run row, in the SAME call — and since `appendStepRun()` is only
  ever invoked from inside `startFmsInstance()`'s or `completeFmsStep()`'s own
  `runInTenantTransaction` scope (confirmed: both wrap their entire body in one already),
  the run insert and its audit insert are atomic with everything else that transaction
  does (TAT computation, the step-completion update, chained `emitFmsEvent`, etc.) — a
  failure anywhere rolls back the run AND its audit row together, never one without the
  other.
- `revertLeave()` (unchanged this pass — already correct from v1) finds this exact audit
  row later via its existing `entityType === "FMS_RUN"` branch and hands the run back only
  if it's still `Pending` and still held by the buddy — the same asymmetric
  "only revert what is still Pending and still held by the buddy" rule v1 preserved for
  pre-existing work now applies identically to FMS runs born DURING an active leave.

## 2. Recurring-Task creation: atomic audit row for buddy-born occurrences

**Before this pass:** `resolveActiveAssignee()` (v1) correctly resolved the buddy for a
newly generated occurrence's `assignedTo`, but recorded NO `leave_reassignments` audit
row for it — `revertLeave()` had no way to find and hand back a recurring occurrence that
was born on the buddy during the leave (as opposed to one that existed before activation
and got redirected by `activateLeave()`, which does audit correctly). This was a real gap
left open by v1, not explicitly flagged in its "Known residual gap" section (which only
named `fms/engine.ts`) — found by inspecting `revertLeave()`'s own revert logic against
what `resolveActiveAssignee()` actually left behind.

**Fix:** `resolveActiveAssigneeWithAudit(orgId, userId)` — new export in
`reassignment.ts`, same resolution as `resolveActiveAssignee()` but also returns the
leave's own `id` (or `""` when nobody is on leave). `recurringGenerator.ts`'s
`createOccurrenceIdempotently()` now wraps the Task insert (`createRecurringOccurrence`)
and, when a leave id was returned, a `leave_reassignments` audit insert
(`entityType: "TASK"`, `originalAssignee` = the rule's own `Doer_ID`, `buddyId` = the
resolved assignee) inside one `runInTenantTransaction(orgId, ...)` — so a crash between
the Task insert and the audit insert rolls back the whole occurrence, never leaving a
Task reassigned to a buddy with no audit trail. The existing 23505
(`tasks_org_id_recurring_id_due_date_unique`) idempotent-duplicate catch wraps the whole
transaction attempt, unchanged in behavior (a concurrent/retried duplicate-cycle insert is
still treated as "already generated", not an error).

`revertLeave()` itself needed NO changes for this — its existing `entityType === "TASK"`
branch already handles any audit row shaped this way identically to one `activateLeave()`
wrote.

## 3. Durable natural-cycle identity across midnight — INSPECTED, already covered by v1,
   no further schema change proposed

Re-verified v1's own claim by reading `recurringGenerator.ts` and
`drizzle/0031_tasks_recurring_cycle_unique.sql` directly (not trusting the v1 report
blindly, per instruction): every occurrence this generator creates — both the Daily path
and the non-Daily/carry-forward path via `findMostRecentScheduledDay()` — is stamped with
`dueDate: \`${today}T23:59\`` where `today` is the GENERATION day (`todayIST()`), not the
cycle's own natural day. A missed Weekly/15D/Monthly/Quarterly/Yearly cycle whose natural
day was yesterday (or further back, within `LOOKBACK_DAYS`) and gets generated TODAY
(carried forward past a holiday/weekly-off) is stamped with TODAY's date, not its own
natural day — meaning `(org_id, recurring_id, due_date)` is unique per GENERATION day, not
per logical cycle. Two different cron runs on two different calendar days that both think
they owe the SAME missed natural cycle (e.g. a transient `listTasks()` read failure on
day N meant the in-memory `alreadyGenerated` check incorrectly said "not yet generated" on
day N+1 too, after day N's run had already silently retried and succeeded) would each
produce a row with a DIFFERENT `due_date` (day N's date vs day N+1's date) for the
logically same cycle — the unique index does not catch this, because the index key
literally differs between the two rows.

**This is a real, distinct gap from what v1's 0031 migration actually closes** (0031 only
stops two SIMULTANEOUS/retried calls within the SAME generation day from double-inserting
— confirmed by reading the migration SQL and the generator's own doc comments, which say
exactly this: "two cron runs ... on the same day"). The task description's framing
("0031's due_date uniqueness only prevents same-day duplicates, not a cycle CARRIED
FORWARD across midnight") is accurate and is NOT fully closed by v1.

**Why no code fix was attempted this pass, and no schema change is proposed yet:**
closing this properly needs a durable per-cycle identity key that is independent of which
day the occurrence actually got generated on — e.g. a stored `natural_cycle_start_date`
column (computed once per rule invocation from `findMostRecentScheduledDay()`'s own
return value, not from `todayIST()`) with its OWN unique index
`(org_id, recurring_id, natural_cycle_start_date)` replacing or supplementing the current
`due_date`-keyed one. This is a genuine new column — `tasks` has no existing field that
already encodes "which natural cycle does this occurrence belong to" independent of its
due date (`recurringId` identifies the RULE, `dueDate` identifies the GENERATION day, not
the cycle). Per this task's own explicit instruction, a subagent finding a real schema gap
must STOP and report it rather than editing `src/db/schema/**` or generating a migration
— this is exactly that case, so the implementation is intentionally left as a proposal
below rather than attempted.

### Proposed schema change (for parent review/application — NOT applied)

- Table: `tasks` (`src/db/schema/tasks.ts`).
- New column: `natural_cycle_start_date` — type `date` (calendar date, no time-of-day,
  matching `holiday_list.date`'s own precedent in the same file), nullable or defaulted to
  `''`/the row's own `dueDate`'s date portion for backfill safety on existing rows,
  `NOT NULL DEFAULT ''` if a sentinel-empty convention is preferred (matching this
  codebase's existing `recurringId`'s own `''`-for-one-off convention) — parent's call on
  exact nullability.
- Populated by `recurringGenerator.ts` at insertion time as the ISO date
  `findMostRecentScheduledDay()` actually returned for the non-Daily path (or `today`
  itself for the Daily path, which has no carry-forward concept and is always its own
  single-day cycle) — NOT `todayIST()` unconditionally.
- New partial unique index, replacing or alongside the existing
  `tasks_org_id_recurring_id_due_date_unique`:
  `tasks_org_id_recurring_id_natural_cycle_unique` on
  `(org_id, recurring_id, natural_cycle_start_date)`, same
  `WHERE recurring_id <> ''` partial-index scoping as the existing one (one-off Tasks are
  unaffected).
- Why this and not reusing `due_date`: `due_date` is already load-bearing for the UI/MIS
  ("when is this occurrence due") and must keep reflecting the day it was actually
  generated (today), which is correct and should not change — the fix needs a SECOND,
  independent column for "which cycle", not a repurposing of `due_date`.
- Migration: would need `npx drizzle-kit generate` run by the parent (or whoever owns
  schema changes) against the real schema, generating a new numbered migration after 0031
  — not generated or hand-written by this pass, per the no-schema-touch constraint.
- Generator change needed alongside (not yet made): `createOccurrenceIdempotently()`'s
  `isUniqueViolation()` check would need the new constraint name added (can coexist with
  the existing one — a genuine retry will trip the new constraint even in cases the old
  one wouldn't catch, which is the whole point of adding it).
