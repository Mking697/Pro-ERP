## 1. First slice and non-goals

Implement a **Recorded Job Cost Sheet (provisional valuation)** for one tenant-owned production plan, using recorded material issues, completion-ledger output, explicit cost inputs and classified received General PO expenses. It is a management reconciliation, not proven historical inventory cost, GL posting or stock revaluation.

First writable/finalizable path: non-FMS plan, `Completed`, with reconciled `Production` issues and exactly one compatible `Production_Output` completion event through the sheet cutoff. In-progress plans may preview/save incomplete Drafts. Plans with any `fms_runs.contextRef = PRODUCTION_PLANS:<planId>` are visible with source diagnostics but **not finalizable in this slice**; no substitution of start quantity. Reject Cancelled plans for new sheets. Missing source evidence stays unavailable.

Retain BOM-derived issue and completion-quantity caveats even when the provisional sheet is finalizable. “Finalized” freezes a reproducible recorded-basis valuation; it does not certify measured consumption, independently inspected good output or historical actual cost. Stronger actual-cost evidence remains explicitly unavailable.

Do not modify `src/lib/costing/{types,engine,domain,service}.ts` or estimated snapshots to add this feature. Add sibling job-costing DTO/domain/service modules and separate tables/routes. No recursive BOM explosion, stock correction, labour time-tracking, depreciation, FMS-template remediation, order profitability or generic public sharing. The later cross-module entry-detail/Excel/CSV/Admin-correction requirement remains separate scope; this slice does not implement that rollout.

## 3. Source eligibility, valuation and completeness rules

### Material and output reconciliation

- Cutoff: validated `YYYY-MM-DD` at end of day IST, as already used by `src/lib/costing/engine.ts:20`. Store `capturedAt` separately. Current plan state is not an as-of status history; never claim a reconstructed historical workflow state.
- Read all tenant plan material rows and plan-reference ledger rows without silently capped operands. Each admitted material issue must be positive `Out/Production`, exact plan reference, expected SKU and matching snapshotted material/current item UOM, timestamp through cutoff. Retain event ID, timestamp and actor. In the narrow start-once writer expect one issue per positive consumed SKU; duplicate/missing/unknown-SKU events, future-start cutoffs or disagreement with `consumedQty` make source reconciliation incomplete, not a guessed aggregation.
- Use issue ledger quantities as the single operand after reconciliation. Preserve the material snapshot required/consumed values for comparison. No fresh BOM multiplication, parent-component explosion or receipt-value addition. Nested Product components remain stock SKU leaves.
- Non-FMS output: require tenant, exact plan reference, `In/Production_Output`, product SKU, positive quantity, compatible nonblank UOM and timestamp through cutoff. First finalizable path requires one event and current `Completed` plan. Missing/multiple events, wrong UOM, any FMS run or conflicting product/reference evidence yields unavailable output and blocks finalization. Do not coalesce missing/unknown to zero.
- Extra issues/returns/rework/scrap do not have an established dedicated plan-cost source in the inspected PPC writer. Surface plan/run-linked noncanonical movements as diagnostics; do not infer their meaning from remarks or net them automatically. Ambiguous linked quantity evidence blocks finalization. Truly unlinked Manual/Adjustment movements cannot be attributed reliably and must be disclosed as an uncaptured limitation, not claimed absent.

### Material valuation

- For every reconciled issue use a **provisional issue-date rate**, not a future purchase rate: latest eligible compatible received-purchase agreed rate recorded no later than that issue timestamp, otherwise explicitly approved standard effective no later than the issue's IST calendar date. This is a conservative specialization of approved as-of costing; issue-date eligibility must be tested independently of sheet-date cutoff.
- Adapt the exact tenant/indent/PO-line/SKU/UOM/event uniqueness checks in `src/lib/costing/service.ts:36-46`; exclude cancelled/invalid sources and preserve warnings. Query eligible rates across the tenant SKU, not only indents linked to this job, so existing-stock issues can be valued. Stable tie-break by timestamp and source identity; persist all selected IDs.
- Purchase `newPrice ?? oldPrice`, never truthy fallback. Invalid latest rate may fall back only to an approved standard, not an invented rate/cheapest vendor/older convenient rate. Same-date standards use the existing effectiveDate/approvedAt/id ordering (`engine.ts:29-32`); disclose retrospective approval/capture date. A standard is an explicit costing approval, not proof the rate existed at physical consumption.
- Snapshot `valuationKind=PurchaseAgreedProvisional|ApprovedStandardProvisional|Missing`, rate/date, currency INR, UOM, PO line/receipt or standard IDs, approval metadata and issue ID. No stock historical cost snapshot exists; **both** purchase-based and standard valuations remain provisional. Changes to source prices cannot alter saved finalized sheets.
- Use decimal strings/fixed-point validation and explicit line rounding, following `src/lib/costing/validation.ts` primitives; never route recorded quantities through the BOM-only estimated engine. Missing versus approved zero stays distinct. No inferred UOM conversion, currency conversion, GST, freight or landed-cost uplift.

### General PO expense classification and allocation

- Present ordered/committed lines separately, informational only. Cost eligibility requires exact same-tenant header/line join, `header.planId=sheet.planId`, status Completed, nonnull `receivedAt<=cutoff`, nonblank receivedBy, finite `0<=receivedQty<=qty`, finite nonnegative rate/amount and consistent ordered amount. Null, overreceived or malformed rows stay unavailable with reasons; no clamp or treating ordered quantity as received. Zero received is explicitly not cost-bearing.
- Since receipt writer is one-shot, header receipt time plus captured line facts is the available received-record basis, **not** event-level historical service acceptance or evidence of physical receipt. Persist its limitation and fingerprint. If historical data cannot support that single completion record, exclude it; never invent line receipt timestamps.
- Each linked line must have an explicit decision: `DirectExpense`, `FactoryOverhead`, `Commercial`, `ExcludedCapital` or `ExcludedOther`; no default financial inclusion. Unclassified eligible candidates block finalization until classified or explicitly excluded with reason. Unreceived commitments stay outside totals.
- A costing-granted live actor records reason/time and allocation basis; selected allocations are deliberate approvals. Capital defaults to excluded, not a full one-job charge. No depreciation engine in this slice. Only this plan's explicitly linked sources are allocatable; cross-plan/common unlinked PO pools are deferred.
- Eligible pre-tax cap = receivedQty × rate rounded to cents, additionally bounded by validated ordered amount. Store source facts and allocated amount. Partial allocation must give a basis and reason for the unused balance. Total active allocation across heads/sheets for one General PO line cannot exceed the cap; no duplicate line within a sheet. Taxes remain excluded. Source-backed General expense must not also appear as an entered manual DirectExpense: manual entries require distinct evidence/reason and server rejection of duplicate referenced sources.

### Manual approved charges and null semantics

- Labour: approved hours × costing hourly rate or explicit per-piece quantity × rate. Factory overhead: approved per-good-unit, labour-hour or machine-hour quantity × rate; Commercial separately. Manual DirectExpense: explicit batch amount/rate with distinct evidence, not a bypass for an ineligible General PO line. No automatic salary or elapsed-TAT conversion.
- Each head requires explicit `Entered` or `NotApplicable` with reason; absent inputs mean Unknown, not zero. Entered charges store quantity/unit/rate, explanation, evidence reference (non-secret), live approvedBy/approvedAt. These are approved costing inputs, not independently sourced historical payroll/machine actuals. For per-unit charges use admitted recorded output, never planned/start quantity. Explicit zero is valid with reason.
- `sourceComplete` means eligible quantities and classifications reconcile. `valuationComplete` means all admitted materials/charges are valued and heads decided. `canFinalize` additionally requires eligible completed non-FMS plan, available positive output and no blocking diagnostics. Do not call these `actualCostComplete`.
- Manufacturing = materials + labour + direct expenses + factory overhead; fullCost = manufacturing + Commercial. Missing material/required head makes the affected total and downstream totals null; expose known subtotals. `perGoodUnit = fullCost / recordedOutput` only with available positive output, else null. No selling price, margin, order revenue or profit fields in this slice.

## 4. Proposed DTO and endpoints (new, not current API)

Add client-safe `src/lib/job-costing/types.ts`; sibling validation/engine/source/domain/service modules. Use decimal strings for all quantities/rates/money, ISO strings for instants, stable diagnostic codes plus text; never accept client source facts/totals/actors.

```ts
JobCostInput = {
  planId: string; asOfDate: string;
  headDecisions: { head: 'Labour'|'DirectExpense'|'FactoryOverhead'|'Commercial';
    status: 'Entered'|'NotApplicable'; reason: string }[];
  charges: { id: string; head: CostHead; description: string;
    basis: 'Batch'|'PerGoodUnit'|'LabourHours'|'MachineHours'|'PerPiece';
    quantity: string; rate: string; reason: string; evidenceRef: string }[];
  generalDecisions: { lineId: string;
    classification: 'DirectExpense'|'FactoryOverhead'|'Commercial'|'ExcludedCapital'|'ExcludedOther';
    allocatedAmount: string; basis: string; reason: string }[];
}
JobCostCalculation = {
  input: JobCostInput; capturedAt: string; sourceFingerprint: string;
  plan: { planId: string; jobNo: string; productSku: string; productName: string;
    productUom: string; bomId: string; bomVersion: string; status: string };
  materials: JobMaterialFact[]; output: JobOutputFact;
  generalSources: JobGeneralSourceFact[]; charges: ApprovedJobCharge[];
  totals: JobCostTotals; sourceComplete: boolean; valuationComplete: boolean;
  canFinalize: boolean; valuationStatus: 'Provisional'|'Incomplete';
  limitations: string[]; diagnostics: { code: string; blocking: boolean; sourceIds: string[]; message: string }[];
}
JobCostSheet = {
  id: string; planId: string; productSku: string; revision: number; version: number;
  status: 'Draft'|'Finalized'; supersedesId: string|null;
  calculation: JobCostCalculation; createdBy: string; createdAt: string;
  updatedAt: string; finalizedBy: string|null; finalizedAt: string|null;
}
```

`CostHead` above is the existing client-safe four-value union, imported type-only without changing estimated types. `JobMaterialFact` contains SKU/name/UOM, plan required/consumed decimal values, issue `{id,timestamp,quantity,userId}` facts, valuation fields from §3 and nullable amount. `JobOutputFact` contains nullable quantity/UOM, basis `CompletionLedger|Unavailable`, ledger/run IDs, timestamp, and explicit non-measured caveat. `JobGeneralSourceFact` contains PO/line/plan IDs, status, ordered/received facts/date/actor/rate/amount/cap, decision, allocated amount and source fingerprint; excluded and committed rows remain distinguishable. `ApprovedJobCharge` adds server appliedQuantity/amount/approvedBy/approvedAt. `JobCostTotals` exposes knownMaterialSubtotal, nullable material/labour/directExpenses/factoryOverhead/manufacturing/commercial/fullCost/perGoodUnit and known entered subtotals; it must not reuse the estimated type whose non-material heads cannot be null.

## 7. Unresolved evidence and safe defaults

- **Historical inventory valuation:** absent in quantity ledger. Use approved provisional rates with provenance; never label actual FIFO/WAC. No retroactive stock revaluation.
- **Independent consumption/output:** start issues are BOM-derived; non-FMS completion repeats start/fallback quantity. Show recorded basis permanently. Do not claim independently measured good output. Dedicated measured issue/return/scrap/QC capture is later work.
- **FMS terminal-good evidence:** no immutable action semantic snapshot or guaranteed pass-field mapping. Block finalization for FMS plans now; keep their run/ledger diagnostics visible. Extending output writers requires its own reviewed slice.
- **General receipt quality:** one header time, nullable/uncapped line receipt values and no durable receive replay. Strictly exclude malformed/unreceived amounts, explicitly classify and cap legitimate received inputs. Source-writer correction/idempotency work is not silently included here.
- **Labour/machine hours and pools:** no demonstrated plan-linked approved actual cost source. Require explicit approved inputs or reasoned NotApplicable; otherwise incomplete. Do not use monthly payroll, TAT or whole asset purchases as cost.
- **Order margin:** free-text plan orderNo is not an allocation. Leave revenue/profit unavailable until explicit tenant-owned order-line allocation exists.
- **Release/runtime acceptance:** estimated browser/print/mobile and migration lineage remain pending context, not retroactively proven by this document. No live records were queried and no tests/builds/migrations were executed for this design.

Document acceptance: source references identify existing writers and their limits; proposed APIs/schema are explicitly future work; first finalizable boundary is non-FMS recorded/provisional only. Parent verification precedes coding.

## J4 implementation record and frozen decisions (2026-10-23)

Implemented as a sibling module, not an edit to `src/lib/job-costing/store.ts` (left completely untouched — frozen per the J3 note above): `src/lib/job-costing/finalize.ts` exports `createJobCostFinalizeDomain(store: JobCostFinalizeStore): JobCostFinalizeService` (pure, DB-free; `finalize(id, raw, key): Promise<JobCostSheet>`) and `createDbJobCostFinalizeStore(authorize, buildFacts): JobCostFinalizeStore` (real wiring over `runIdempotentTenantMutation` and `job_cost_sheets`/`job_cost_lineages`/`job_cost_source_allocations`, dynamically imported like `store.ts`'s own production store). No HTTP route wires this yet (J5 scope); no migration was generated or applied (schema unchanged from J3 — the three tables already exist, only now written to).

**Finalize sequence** (one `job-costing.v1.finalize` idempotent mutation, mirroring `src/lib/costing/domain.ts`'s `finalize` precedent for the version/status CAS, extended with lineage/allocation steps section 5 requires): (1) load the Draft, require `status === "Draft"` and `version === expectedVersion`, require the submitted `sourceFingerprint` to match the saved one; (2) rebuild facts through the injected `buildFacts` (J2 adapter) and recompute through `store.recompute` (production wiring always `calculateJobCost`, the real unmodified J1 engine — see point 3 below) inside the same transaction; a mismatched fresh `sourceFingerprint`, or a recompute that throws, is a 409 "evidence changed" error, never a silent reprice; only once the fingerprint matches are the recomputed `sourceComplete`/`valuationComplete`/`canFinalize` flags trusted (they are guaranteed identical to the stored ones by determinism); (3) collect one allocation claim per cost-bearing (DirectExpense/FactoryOverhead/Commercial) General PO line decision, rejecting a duplicate source line within one sheet defensively (400) even though the real engine/zod schemas already make that structurally unreachable; (4) validate `supersedesId` against `job_cost_lineages.activeFinalizedSheetId` (first finalize requires no active pointer yet; successor finalize requires an exact match) and compute each claimed line's real cap headroom from `listActiveAllocations` (ACTIVE rows across any sheet, **excluding only an explicitly superseded parent's own rows**) — any claim whose request plus other active claims would exceed `min(receivedQty*rate, orderedAmount)` in cents blocks the *whole* finalize, never a partial/clamped allocation; (5) attempt the lineage CAS (`createLineage` for a first finalize, `advanceLineage` for a successor) **before** any sheet/allocation write — a `false` return (lost race) throws a 409 with nothing written; (6) only on a successful CAS: mark the sheet `Finalized` (version+1, `finalizedAt`/`finalizedBy`), insert the new allocation rows, and (successor only) deactivate the parent's allocation rows. All of this executes inside the one `runIdempotentTenantMutation` transaction — a real Postgres commit/rollback covers every write together, so a thrown error at any step leaves nothing partially applied.

**Concurrency mechanism** (section 5's "DB-level uniqueness/locking" requirement): `createLineage`'s production implementation is a real `INSERT ... ON CONFLICT (orgId, planId) DO NOTHING` against `job_cost_lineages`' existing unique index, returning whether a row was actually inserted; `advanceLineage` is a real conditional `UPDATE ... WHERE active_finalized_sheet_id = $from` (Postgres re-evaluates the predicate under the row lock after any concurrent writer commits, so a stale `$from` yields zero rows), returning whether the pointer actually moved — the identical compare-and-swap shape as `store.ts`'s own optimistic-version `save()` update. Both return a boolean instead of throwing so `finalize.ts` decides the resulting domain error itself. The DB-free test suite simulates the race by running two `finalize()` calls through `Promise.allSettled` against the same in-memory lineage map (whose `createLineage`/`advanceLineage` fixture implementations are synchronous check-and-set, exactly mirroring the real CAS's atomicity) and asserts exactly one settles fulfilled and the other rejects with `status: 409`, with the losing Draft left completely untouched (still `Draft`, version 1, no allocation rows).

**Frozen parent decisions for J5:**

1. **`source.ts`'s `activeAllocatedAmount` placeholder (`"0.00"`) is intentionally left unchanged.** The J1 engine's own in-Draft cap check (`engine.ts`'s `GENERAL_ALLOCATION_EXCEEDS_CAP`) therefore still always assumes zero other active claims when previewing/saving a Draft — this is the documented "Preview allocations do not reserve source caps" limitation (`engine.ts`'s `LIMITATIONS`), unchanged by this stage. The AUTHORITATIVE cap check against real active allocations happens only inside `finalize.ts`'s own `listActiveAllocations` arithmetic at finalize time, which is a separate, additional, more accurate check than the engine's Draft-time one — not a replacement for it. J5 should not present a Draft's `eligibleCap`/`activeAllocatedAmount` as a reservation guarantee; only a `Finalized` sheet's allocation rows are authoritative.
2. **`JobCostFinalizeStore.recompute` is an injectable hook, not a hardcoded call to `calculateJobCost`**, purely so the DB-free test suite can exercise `finalize.ts`'s own defensive duplicate-source-line guard against a crafted calculation shape (real `jobCostInputSchema`/`jobCostFactsSchema` uniqueness refinements make a genuine duplicate lineId structurally unreachable through the real engine). `createDbJobCostFinalizeStore`'s production wiring binds this directly to the real, unmodified `calculateJobCost` import — there is no second/divergent engine implementation anywhere. J5 must keep this binding as-is.
3. **`JobCostAllocationRecord.facts` stores a small `{lineId, poId, planId}` pointer**, not a full `JobGeneralSourceFact` evidence snapshot — the authoritative evidence for both the active sheet and every prior immutable finalized sheet already lives in `job_cost_sheets.calculation.generalSources`. J5/reporting should read the sheet snapshot for full evidence and use the allocation row only to know which sheet/head/amount is the currently active claim on a given PO line.
4. **Lineage-CAS-before-sheet/allocation-write ordering is deliberate** and must not be reordered without re-reading `tests/job-costing-finalize.test.ts`'s race-simulation assertions, which depend on a losing finalize writing nothing at all (not just "nothing durable").
5. **No HTTP route/service entry point wires `createDbJobCostFinalizeStore` yet** (same convention as `store.ts`'s own `createDbJobCostDraftStore`/`createDbJobSourceStore` split) — `authorize`/`mutate`/`buildFacts` are all left to the caller.
